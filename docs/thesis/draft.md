## 要旨・Abstract

### 要旨（日本語・骨子）

DCC ツール（Houdini など）は機能の進化が速く、バージョンアップに伴う機能の削除・統合・UI の変更に、既存の学習資料が追いつかない。デザイナーは、公式ドキュメントよりも動画チュートリアルを参照する傾向が指摘されているが、動画はツールの更新で陳腐化しやすい。本研究では、この課題に対し、**検索拡張生成（RAG）で Houdini の公式ドキュメントを検索し、Houdini の中で実際にノードを組み立てて検証しながら、ステップバイステップのチュートリアル（手順書と、音声つきの解説動画）を自動で生成するシステム**を開発した。システムは、Houdini 内のパネル、Cloudflare Workers 上の検索・認証・集計基盤、動画生成エンジン（RAGReel）からなる。回答には、必ず参照元のドキュメント（出典）を示す設計とした。

評価として、【要記入: 人数】名の学生を、本システムを使う群と、公式ドキュメント・Web 検索のみの群に分け、固定課題を行う実証実験を行った。学習コストは、主観評価（難しさ・わかりやすさの 5 段階）を主な指標とし、所要時間・操作ミス・到達を補助とした。結果、【要記入: 主な結果。**効果量と人数を併記**】。一方で、【要記入: 限界・できなかったこと】。

**キーワード:** Houdini、DCC ツール、RAG、LLM、チュートリアルの自動生成、学習コスト　【要確認: 大学の指定する個数・形式】

### Abstract（英語・骨子）

Digital content creation (DCC) tools such as Houdini evolve quickly, and existing learning resources, especially video tutorials, become obsolete as features are removed, merged, or redesigned. We developed a system that retrieves the official documentation (RAG), builds and verifies node networks inside Houdini with an LLM agent, and automatically exports the process as a step-by-step written tutorial and a narrated video, always presenting the source documents. We evaluated it with 【N】 students in a between-group experiment (the system vs. official documentation and web search only) on a fixed task. Learning cost was measured mainly by subjective ratings of difficulty and clarity (5-point scales), with completion time, errors, and task completion as supporting measures. 【Results: effect sizes with sample sizes.】 【Limitations.】

**Keywords:** Houdini, DCC tools, retrieval-augmented generation, large language models, automatic tutorial generation, learning cost

### 1.2 DCC ツールの進化と、学習資料が追いつかない問題

DCC ツール（Houdini など）の機能は、急速に進化している。バージョンアップのたびに、機能の削除・統合・UI の変更が起き、既存の学習資料が追いつかない。例として、Houdini の Solaris の導入や、バージョンごとのノード仕様の変更がある。（シート §3）

その結果、**制作者が、機能の進化に置いていかれる**状態が常態化している。本研究では、これを、「ツールの新機能・変更機能に対し、既存の学習資料では対応できず、自力で習得するコストが増大した状態」と定義する。（シート §3）

### 1.3 デザイナーの学習の実態

デザイナーは、テキスト量の多い公式ドキュメントを参照する習慣が低く、実際には、YouTube などの動画チュートリアルで手順を確認しながら制作するケースが大半を占める、と考えられる。この傾向は、先行研究でも指摘されている（van der Meij & van der Meij, 2014; van der Meij et al., 2018）。しかし、動画は、ツールの更新によって陳腐化しやすいことが、継続的に検証されている（arXiv:2301.13617）。（中間報告 §1 の [1]〜[3]）

【要確認】「大半を占める」は、シートの記述。**調査・統計の出典があれば付ける**（なければ「〜と考えられる」にとどめる）。上の文献が、この主張をどこまで支えるかは、**原典で確認する**。

### 1.4 生成 AI の広がり

大規模言語モデル（LLM）が、文書の検索と組み合わせた回答（RAG）や、ツールを呼び出して作業を進めるエージェントとして、使われるようになった。DCC ツールでも、外部の AI から操作する仕組みが、複数公開されている（章 2）。【要確認: 一般的な動向の記述には、文献を付ける】

### 1.5 研究の目的

RAG で Houdini の公式ドキュメントを検索し、Houdini の中での実際の操作で検証しながら、ユーザーの質問に応じたステップバイステップのチュートリアルを自動生成するシステムを構築する。これにより、デザイナーが DCC ツールの新機能・変更機能を習得する際の、学習コストを削減できるかを検証する。基盤の汎用性が確認できた場合は、Blender や Unity など、他のツールへの展開可能性も考察する。（シート §2・中間報告 §2）

### 2.2 RAG とハイブリッド検索

RAG は、外部の文書を検索して、LLM の回答の根拠にする枠組みである（Lewis et al., 2020）。本システムは、意味検索（ベクトル）とキーワード検索（BM25 系）を、順位の統合（Reciprocal Rank Fusion。Cormack et al., 2009）で組み合わせる、ハイブリッド検索を用いる。【要確認: 原典で、引用の内容・書誌を確認】

### 2.3 出典の提示とハルシネーションの抑制

回答に、参照元を必ず付ける（出典の強制）ことが、ハルシネーションの抑制に有効であることは、医療 AI の領域で報告されている（MDPI Applied Sciences, 16(6), 3013, 2026。中間報告の [4]）。【要確認: 原典で、内容・書誌（著者・題）を確認。Houdini のような DCC の領域に、そのまま当てはまるかは、別の問題として書く】

### 2.4 LLM のツール利用エージェント

推論と行動を交互に行うエージェントの枠組み（ReAct。Yao et al., 2023）や、ツール呼び出しによるエージェントが、広く使われている。コード生成では、コンパイル・テストの成否という明確な成功指標がある。一方、Houdini のノードグラフは、「cook エラーが出ない」ことと「意図した見た目になっている」ことの両方が必要で、後者は、テキストだけでは検証できない（4・5 章）。【要確認】

### 2.5 Houdini × AI の道具（調査済み・2026-10-23）

公開されている近い道具として、fxhoudinimcp・capoomgit/houdini-mcp・oculairmedia/houdini-mcp・Houdini21MCP・Synapse・dcc-mcp-core を比較した（調査方法: 各リポジトリの公開ページ（README）と GitHub の検索 API を読んだ。**どの道具も、実際には、インストール・実行していない**）。

- これらは主に、**外部の AI（Claude・Cursor など）から、Houdini を操作する**ための橋（MCP サーバー）である。ノード・USD・シミュレーション・レンダリングなどを、広く操作できる。ツール数は、公開された説明で、215（fxhoudinimcp）・43（oculairmedia）・12（Houdini21MCP）・139（Synapse）などである。

### 2.7 学習の評価

学習の負担は、認知負荷理論で議論される（Sweller, 1988）。本研究では、「学習コスト」を、課題シートの定義どおり、**主観評価（難しさ・わかりやすさの 5 段階）を主な指標**とし、所要時間・操作ミス・到達を補助とした（6 章）。使いやすさの尺度に SUS（Brooke, 1996）があるが、本研究は、課題に合わせた独自の設問を用いた。統計は、群間の比較に Mann-Whitney U 検定と効果量を用いる（Cohen, 1988; Cliff, 1993）。【要確認: 設問の妥当性の扱い】

### 4.1 解決手法の候補と比較

| 手法 | 内容 | 利点 | 課題 |
|---|---|---|---|
| A. 公式ドキュメント・動画 | 既存の資料で、学習者が自力で探す | 正確・無料 | 題材・版・レベルに合わせにくい。探す負担。動画は更新で陳腐化する |
| B. 汎用 LLM チャット | 質問に、LLM が自由に答える | 手軽 | 最新の版・資料の根拠が弱い。出典が無い。実際に動くかの検証が無い |
| C. 外部 AI が Houdini を MCP で操作 | AI が、Houdini を直接、広く操作する | 操作の幅が広い | 目的は「操作」で、教材ではない。任意のコード実行を持つ道具もあり、安全面の配慮が要る |
| D. RAG ＋ パネル内での操作と検証 ＋ 教材の自動生成（本システム） | 公式資料を検索し、サンドボックスで組み立てて検証し、手順書・動画に書き出す | 根拠（出典）つき・動作の検証つき・教材として届く | 実装が大きい。LLM の出力が揺れる。生成に時間がかかる |

### 4.2 採用した方針とシステムの構成

D を採用した。中間報告では、システムを、①チャットボット（対話窓口。LLM 使用）、②Houdini 操作の代理実行・記録、③RAG データサーバー（ヘルプ文書のハイブリッド検索の基盤）の 3 つのコアと、付随ツールとして④生成した手順を解説動画に変換する **RAGReel** の、計 4 つのパーツで説明している。現在の実装との対応は、5.1 に示す。

- 流れ: 質問 → RAG で関連ドキュメントを取得 → LLM がチュートリアルを生成（Houdini で組み立てて検証）→ 出典と合わせて提示。（シート §4）
- 入り口の負担 → **作業中の Houdini の中で、質問・手順の案内ができる**パネル。
- 教材の用意の負担 → **依頼から、手順書・動画を自動で生成**。
- 再現性 → **実際に Houdini で組み立てて、cook エラーと見た目を確かめてから**書き出す。さらに、手順の抜けを検出して補う。

パネルは、利用者ごとの API キーで、Worker にだけ接続する。

### 5.2 Houdini パネル

作業中の Houdini の中で、質問（Chat）、ドキュメント検索（Docs）、手順の案内（Guide）、チュートリアル生成（Tutorial）、動画（動画）、実験の課題（課題）を行う。Guide は、手順が指すノードを、ネットワークエディタで選び・表示して追従する。実験での指摘（「違うオブジェクトが表示される」「ショートカットが毎回出て邪魔」「パスが省略される」など）を受けて、改善した（5.8）。

### 5.3 チュートリアル生成エージェント

LLM が、**19 個のツール**（Houdini の操作 15、文書の検索 2、完了の申告 2）を呼びながら、サンドボックスの中で、ノードを組み立てる。ユーザーのシーンには触れない。

- **検証**: cook エラーの有無と、ビューポートの画像による見た目の確認（`confirm_tutorial`）。
- **終了の救済**: 「ノードを作らずに終わる」「下書きを出したが確定しない」「ノードを作ったが提出しない」の失敗を個別に検出し、救済の文を送る。反復の上限（80 回）と費用の上限（$5）に近づいたら、仕上げを促す。
- **題材別の達成基準・手がかり**（炎・煙・竜巻・雲・RBD・リグ）と、**手順の抜けの検出**（ノード・値・コード・接続）。
- **出力**: Markdown の手順書、ノードグラフの JSON、画面の画像。

### 5.4 解説動画の生成（RAGReel）

手順書と画面から台本を作り、音声（SAPI・VOICEVOX・クラウド TTS）つきの動画を書き出す（QML で描画し、FFmpeg で VP9/Opus の WebM に）。既定は 1920×1080・30 fps。字幕は、読み上げ用のカタカナとは別の表記を持てる。生成直後の動画を、Houdini のパネル内で、その場で再生できる（中間報告 §5）。ギャラリー（Cloudflare Worker＋R2）で、一覧・再生・出典の表示・削除ができる。

書き出しは、描画・色変換・エンコードを別のスレッドで流すパイプラインと、同じ見た目のフレームの使い回しで高速化した。同じ入力（1063 秒・フル HD・30 fps）で、旧版 583 秒 → 新版 139〜182 秒（3.2〜4.2 倍）。画質は、PSNR 中央値 74.2 dB。音声の合成は、クラウド TTS の並列化で 384 秒 → 並列 4 で 95.7 秒（[video-speed.md](../reports/pilot-feedback-2026-11-17/video-speed.md)）。

### 5.5 検索・認証・集計の基盤

ハイブリッド検索（ベクトル＋全文、RRF）、出典つきの回答、ユーザーごとの API キー（ロール・ナレッジの範囲・予算・有効期限）、使用量の追跡、管理画面。D1 にスキーマ（マイグレーション 0001〜0037）を持つ。クラウド側の移行では、バッチ埋め込み API による処理速度の改善と、認証・レート制限の堅牢化を行った（中間報告）。理解度スコアエンジンと、監査ログ（RAGAuditLogger）も実装した（シート）。【要確認: 現行の Worker での位置づけ】

### 5.6 実証実験のための機能

「課題」タブ（開始・終了・アンケート・中断からの再開）、課題の割り当て（登録順の番号から、3 題材 × 2 条件の 6 通り）、受け付ける回の管理画面での切り替え、条件の割り当ての切り替え、回答の一覧（自由記述・計測値）と CSV、群間の比較の集計。cook エラーのノード数を、20 秒ごとに採取する。

### 5.7 配布と運用

zip（`install.cmd`）と動画エンジンのインストーラーで、別の PC に配布する。管理者権限は不要。導入の自己診断を出力する。Worker は `wrangler` でデプロイし、D1 のマイグレーションは、先に適用する（表を先、Worker を後）。

### 6.5 結果（定性：自由記述・感想）

実験で得られた感想（記録のまま。**発言者の人数・属性は、整理して書く**【要記入】）:

**良かった点**
- 操作・見るものが、Houdini の中でほぼ完結していて、他の画面に思考が散らず、集中できた。
- 「段取りを決めてからリファレンスを集めて作る」流れだと時間がかかるが、今回は、お題が設定され、実物があり、それを見ながら作って学習できたので、時間が短く済んだ。

**改善の要望**
- ガイドに、違うオブジェクトが表示されることがある。対応するオブジェクトの表示・追従と、UI の強調表示がほしい。
- ショートカットキーは、最初だけ出して、その後は非表示か折りたたみに。パスが省略されていて分からない。どの階層にいるかを表示してほしい。
- チェックボックスやメニューが数字で指定されている。パラメータの場所が出ていない。消す手順は「消す」と指示してほしい。ノードを、どんな目的で使っているかの説明がほしい。
- 省かれている箇所に抜け漏れがあり、同じ手順でやってもできない場合がある。
- タブを切り替えると、別のタブを並行して見られない。接続などの設定のタブが、他のタブと同じ比重に感じる（アイコンやメニューにするべき）。
- 動画: ノード数が増えると見づらい。文字（VEX など）がつぶれる。解像度・fps が低い。出典が出ない（「出典なし」）。まとめて消す機能がほしい。
- 生成: 打ち切りになる割合が高い。時間がかかる。ノードのつなぎ方がきれいでない。竜巻ができていない。

【要記入】アンケートの自由記述の件数・カテゴリ分け（改善の要望／良かった点などに分類し、件数を示す）。インタビューを行った場合は、その結果。

### 6.8 考察【要記入】

次の観点で、結果を解釈する。**結果が出てから書く**。結果が出なかった・差がなかったことも、書く。

- RQ1〜RQ3 への答え（効果量と人数を併記。「傾向」にとどめ、断定しない）。
- 群の差に、**個人差**（Houdini の経験）が混ざっていないか（事前アンケートで確認）。
- システムの**改善**（実験の途中・直前の修正）が、結果に、どう影響したか。
- 実験で見つかった課題の共通点（Guide の追従・表記・生成の安定・動画の見やすさ）と、それが学習の負担に、どうつながるか。
- 「Houdini の中で完結する」ことの意味（集中を妨げない）。
- 出典の提示が、ハルシネーションの認知（不安）に与えた影響。
- **機密性とクラウド依存**: 本システムは、生成の際に、ノード・手順・画面の情報を、外部の API（Claude など）に送る。実験の参加者が、これをどう感じたか（事前・事後のアンケートの自由記述）を確かめ、**完全ローカル推論（Houdini 内蔵の ONNX Runtime の活用。8 章）が必要な場面**を考察する。【要記入: アンケートに、データの送信への抵抗感を問う設問があったか】

### 6.9 限界（必ず書く）

- 少人数・自己選択・自己評価で、結果は一般化できない。
- **実験者と開発者が同じ**で、参加者の評価が甘くなる可能性がある。
- LLM の出力は、毎回変わる。同じ課題でも、結果は揺れる。
- 回（期間）の間で、システムを改善しているため、**期間の差には、使い慣れと改善が混ざる**。
- 1 人 1 回・群間の比較のため、**個人差が群に混ざる**。群の割り振りは、レベルの均等化をしていない（食い違い #5）。
- 計画した対象者の条件（経験 1 年以上など）と、実際の参加者が違う場合、結果の解釈に影響する（食い違い #3）。
- 1 コマ（約 90 分）で、固定課題が収まらない人が出うる。
- 授業での告知で集めた参加者は、自発的な参加者と違う層になりうる。
- 評価率が低いと、評価した人だけの偏りになる（評価率を併記する）。

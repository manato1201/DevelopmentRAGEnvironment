要旨（chapter 0）

論文要旨（日本語・骨子）

Houdini は、ノードを組み合わせて形を作る手続き型の 3DCG ツールであり、表現の幅が広い一方で、ノード・パラメータが多く、初学者が学習の入り口でつまずきやすい。本研究では、【要記入: 一文で、何を作ったか】として、Houdini の公式ドキュメントを検索（RAG）して、実際に Houdini の中でノードを組み立てて検証し、その過程を、手順書と音声つきの解説動画に自動で書き出すシステムを開発した。システムは、Houdini 内のパネル、Cloudflare Workers 上の検索・認証・集計基盤、動画の生成エンジンからなる。

評価として、【要記入: 人数】名の学生を対象に、固定課題（Pyro・RBD・雲のいずれか）を、本システムを使う群と、公式ドキュメント・Web 検索のみで行う群に分けて行う実証実験を行った。主観評価（難しさ・わかりやすさ。5 段階）、所要時間、操作ミス、到達を、群の間で比べた結果、【要記入: 主な結果。数値と人数を併記】。一方で、【要記入: できなかったこと・限界】。

キーワード: Houdini、RAG、LLM、教材の自動生成、学習支援　【要確認: 大学の指定する個数・形式】

Abstract（英語・骨子）

Houdini is a node-based procedural 3DCG tool whose breadth makes it hard for beginners to learn. We developed a system that retrieves the official documentation (RAG), builds and verifies node networks inside Houdini with an LLM agent, and automatically exports the process as a written tutorial and a narrated video. We evaluated it with 【N】 students in a between-group experiment (system vs. official documentation only) on a fixed task (Pyro, RBD, or cloud). 【Results: effect sizes with sample sizes.】 【Limitations.】

Keywords: Houdini, retrieval-augmented generation, large language models, automatic tutorial generation, learning support

1.2 Houdini の学習の難しさ

Houdini は、ジオメトリ・シミュレーション・レンダリングなどを、ノードのネットワークとして組み立てるツールである。手続き型であることが強みである一方、学習の面では、次の困難がある。【要確認: 各点に、出典（公式ドキュメント・文献）か、筆者の実体験・実験の観察を付ける】

  • ノードの種類とパラメータが多く、目的のパラメータの場所が分かりにくい（実験でも、「パラメータ先が出ていない」という感想が出た）。
  • 版（20・21・22）ごとに機能・名称が変わり、手元の版と、解説の版が合わないことがある。
  • 解説が、完成した結果の説明にとどまり、同じ手順でやっても再現できないことがある（省略された手順・値）。

1.3 生成 AI の広がり

2.2 RAG とハイブリッド検索

RAG は、外部の文書を検索して、LLM の回答の根拠にする枠組みである（Lewis et al., 2020）。本システムは、ベクトル検索と全文検索（BM25 系）を、順位の統合（RRF）で組み合わせるハイブリッド検索を用いる（Cormack et al., 2009）。【要確認: 原典で、引用の内容・書誌を確認】

2.3 LLM のツール利用エージェント

推論と行動を交互に行うエージェントの枠組み（ReAct。Yao et al., 2023）や、ツール呼び出しによるエージェントが、広く使われている。コード生成では、コンパイル・テストの成否という明確な成功指標がある。一方、Houdini のノードグラフは、「cook エラーが出ない」ことと「意図した見た目になっている」ことの両方が必要で、後者はテキストだけでは検証できない（章 4・5 で扱う）。【要確認】

2.4 DCC ツールの学習支援・教材の自動生成

【要記入】Houdini・Blender などの学習支援（チュートリアル・インタラクティブな教材・学習システム）の先行事例。調べ方の案: 「tutorial generation」「learning support for 3D modeling software」「intelligent tutoring system」「procedural content」。SideFX 公式のチュートリアル・Entagma などの解説は、静的な教材であり、学習者の題材・レベルに応じて、都度、変わらない点を、比較の軸にできる。

2.5 学習の評価

学習の負担は、認知負荷理論で議論される（Sweller, 1988）。本研究では、「学習コスト」を、課題シートの定義どおり、主観評価（難しさ・わかりやすさの 5 段階）を主指標にし、所要時間・操作ミス・到達を補助とした（章 6）。使いやすさの評価には、SUS（Brooke, 1996）などの尺度があるが、本研究は、課題の項目に合わせた独自の設問を用いた。【要確認: 設問の妥当性の扱い】

2.6 本研究の位置づけ（新規性の整理）

2026-09-22 のメモで、新規性を、次のように整理した。

  • 要素技術としての新規性は、低い。 ハイブリッド検索・LLM のツール利用・OAuth などは、既存の手法・標準である。

3.1 解決したい課題

  1. 学習の入り口の負担: ノード・パラメータが多く、初学者が、どこを触ればよいか分からない。
  2. 教材の用意の負担: 題材・版・レベルごとに、教材を作るコストが高く、少人数のチームや個人では、継続的に整備しにくい。
  3. 再現性: 解説が、省略された手順・値を含み、同じ手順でやっても同じ結果にならないことがある。

3.2 研究の問い（RQ）【要確認: 指導教員と確定】

  • RQ1: 本システムの手順書・動画は、公式ドキュメント・Web 検索のみと比べて、初学者の学習コスト（難しさ・わかりやすさの主観評価）を下げるか。
  • RQ2: 所要時間・操作ミス・到達に、違いは見られるか。
  • RQ3: 生成される教材は、実務の観点から、どの程度の品質・導入価値があるか（専門家評価）。【要確認: 実施できた場合のみ】
  • RQ4: 実験を通じて、どのような課題（生成の失敗・遅さ・UI）が見つかり、どう改善できたか。

3.3 到達目標

  • 依頼文から、Houdini 上で動くノードグラフと、手順書・解説動画を、自動で生成できること。
  • 生成した教材で、初学者が、固定課題（Pyro・RBD・雲）を、時間内に、完了できること。【要記入: 成功基準の数値。分析設計 §8 の「決めること」を確定】
  • 実験の結果を、人数と限界を併記して、報告できること。

3.4 意義とスコープ

意義は、教材そのものを都度生成する点にある。スコープは、Houdini 21・22、固定課題 3 題材、学生（ビギナー）を対象とした実験である。一般化は、しない（少人数・自己選択・自己評価）。

材料: pilot-analysis-design.md §0・§2・§8、houdini21-learning-effect-study.md。

4.1 解決手法の候補と比較

手法 内容 利点 課題
A. 公式ドキュメント・動画 既存の資料で、学習者が自力で探す 正確・無料 題材・版・レベルに合わせにくい。探す負担
B. 汎用 LLM チャット 質問に、LLM が、自由に答える 手軽 最新の版・資料の根拠が弱い。出典が無い。実際に動くかの検証が無い
C. 外部 AI が Houdini を操作（MCP 型） AI が、Houdini を直接、広く操作する 操作の幅が広い 目的は「操作」で、教材ではない。任意のコード実行を持つ道具もあり、安全面の配慮が要る
D. RAG ＋ 操作の検証 ＋ 教材の自動生成（本システム） 公式資料を検索し、サンドボックスで組み立てて検証し、手順書・動画に書き出す 根拠（出典）つき・動作の検証つき・教材として届く 実装が大きい。LLM の出力が揺れる。生成に時間がかかる

【要確認: B・C は、一般的な特徴で、本研究で実測したものではない。C は、公開された説明による（章 2.1）】

4.2 採用した方針

D を採用した。理由は、課題 1〜3（3.1）に、それぞれ、次で対応するためである。

  • 入り口の負担 → 作業中の Houdini の中で、質問・手順の案内ができるパネル。
  • 教材の用意の負担 → 依頼から、手順書・動画を自動で生成。

5.1 全体構成

システムは、3 つからなる。(1) Houdini の中で動く Python パネル（PySide）、(2) Cloudflare Workers 上の基盤（検索・認証・予算・実験の集計。D1・Vectorize・R2）、(3) 動画の生成エンジン（C++・Qt6・FFmpeg）と、公開用のギャラリー。AI の呼び出し（Claude など）と鍵は、Worker だけが持ち、パネルは、利用者ごとの API キーで、Worker にだけ接続する。

5.2 Houdini パネル

作業中の Houdini の中で、質問（Chat）、ドキュメント検索（Docs）、手順の案内（Guide）、チュートリアル生成（Tutorial）、動画（動画）、実験の課題（課題）を行う。Guide は、手順が指すノードを、ネットワークエディタで選び・表示して追従する。実験での指摘（「違うオブジェクトが表示される」「ショートカットが毎回出て邪魔」「パスが省略される」など）を受けて、改善した（5.8）。

5.3 チュートリアル生成エージェント

LLM が、19 個のツール（Houdini の操作 15、文書の検索 2、完了の申告 2）を呼びながら、サンドボックスの中で、ノードを組み立てる。

  • 検証: cook エラーの有無と、ビューポートの画像による見た目の確認（confirm_tutorial）。
  • 終了の救済: 「ノードを作らずに終わる」「下書きを出したが確定しない」「ノードを作ったが提出しない」の失敗を個別に検出し、救済の文を送る。反復の上限（80 回）と費用の上限（$5）に近づいたら、仕上げを促す。
  • 題材別の達成基準・手がかり（炎・煙・竜巻・雲・RBD・リグ）と、手順の抜けの検出（ノード・値・コード・接続）。
  • 出力: Markdown の手順書、ノードグラフの JSON、画面の画像。

5.4 解説動画の生成（RAGReel）

手順書と画面から、台本を作り、音声（SAPI・VOICEVOX・クラウド TTS）つきの動画を書き出す（QML で描画し、FFmpeg で VP9/Opus の WebM に）。既定は 1920×1080・30 fps。字幕は、読み上げ用のカタカナとは別の表記を持てる。ギャラリー（Cloudflare Worker＋R2）で、一覧・再生・出典の表示・削除ができる。

5.5 検索・認証・集計の基盤

ハイブリッド検索（ベクトル＋全文、RRF）、出典つきの回答、ユーザーごとの API キー（ロール・ナレッジの範囲・予算・有効期限）、使用量の追跡、管理画面。D1 にスキーマ（マイグレーション 0001〜0037）を持つ。

5.6 実証実験のための機能

「課題」タブ（開始・終了・アンケート・中断からの再開）、課題の割り当て（登録順の番号から、3 題材 × 2 条件の 6 通り）、受け付ける回の管理画面での切り替え、条件の割り当ての切り替え、回答の一覧（自由記述・計測値）と CSV、群間の比較の集計。cook エラーのノード数を、20 秒ごとに採取する。

5.7 配布と運用

zip（install.cmd）と動画エンジンのインストーラーで、別の PC に配布する。管理者権限は不要。導入の自己診断を出力する。Worker は wrangler でデプロイし、D1 のマイグレーションは、先に適用する（表を先、Worker を後）。

5.8 開発の進め方

実装・検証・ドキュメント化を、1 つの反復として回した。テストは、Houdini 側 806 件、Worker 側 34 件（2026-11-17 時点）。【要確認: 最終の数値に更新】実験の結果を受けた改善（2026-11-17）は、6 つの担当に分けて並行で実装し、さらに、リファクタリングと不備の確認を行った。その過程で、費用の上限の確認漏れ（救済の経路を通らない）や、CSV の式注入の対策漏れなどの不備を見つけて直した。【要確認: 事例として書くか、筆者が判断】

6.5 結果（定性：自由記述・感想）

実験で得られた感想（記録のまま。発言者の人数・属性は、整理して書く【要記入】）:

良かった点
- 操作・見るものが、Houdini の中でほぼ完結していて、他の画面に思考が散らず、集中できた。
- 「段取りを決めてからリファレンスを集めて作る」流れだと時間がかかるが、今回は、お題が設定され、実物があり、それを見ながら作って学習できたので、時間が短く済んだ。

改善の要望
- ガイドに、違うオブジェクトが表示されることがある。対応するオブジェクトの表示・追従と、UI の強調表示がほしい。
- ショートカットキーは、最初だけ出して、その後は非表示か折りたたみに。パスが省略されていて分からない。どの階層にいるかを表示してほしい。
- チェックボックスやメニューが数字で指定されている。パラメータの場所が出ていない。消す手順は「消す」と指示してほしい。ノードを、どんな目的で使っているかの説明がほしい。
- 省かれている箇所に抜け漏れがあり、同じ手順でやってもできない場合がある。
- タブを切り替えると、別のタブを並行して見られない。接続などの設定のタブが、他のタブと同じ比重に感じる（アイコンやメニューにするべき）。
- 動画: ノード数が増えると見づらい。文字（VEX など）がつぶれる。解像度・fps が低い。出典が出ない（「出典なし」）。まとめて消す機能がほしい。
- 生成: 打ち切りになる割合が高い。時間がかかる。ノードのつなぎ方がきれいでない。竜巻ができていない。

【要記入】アンケートの自由記述の件数・カテゴリ分け（自由記述を、改善の要望／良かった点などに分類し、件数を示す）。インタビューを行った場合は、その結果。

6.7 考察【要記入】

次の観点で、結果を解釈する。結果が出てから書く。結果が出なかった・差がなかったことも、書く。

  • RQ1・RQ2 への答え（効果量と人数を併記。「傾向」にとどめ、断定しない）。
  • 群の差に、個人差（Houdini の経験）が混ざっていないか（事前アンケートで確認）。
  • システムの改善（実験の途中・直前の修正）が、結果に、どう影響したか。
  • 実験で見つかった課題の、共通点（Guide の追従・表記・生成の安定・動画の見やすさ）と、それが、学習の負担に、どうつながるか。
  • 「Houdini の中で完結する」ことの意味（集中を妨げない）。

6.8 限界（必ず書く）

  • 少人数・自己選択・自己評価で、結果は、一般化できない。
  • 実験者と開発者が同じで、参加者の評価が甘くなる可能性がある。
  • LLM の出力は、毎回変わる。同じ課題でも、結果は揺れる。
  • 回（期間）の間で、システムを改善しているため、期間の差には、使い慣れと改善が混ざる。
  • 1 人 1 回・群間の比較のため、個人差が群に混ざる。人数が少ないと、差が出にくい。
  • 1 コマ（約 90 分）で、固定課題が収まらない人が出うる。所要時間（約 3 時間）の実測は、ない。
  • 授業での告知で集めた参加者は、自発的な参加者と違う層になりうる。
  • 評価率が低いと、評価した人だけの偏りになる（評価率を併記する）。

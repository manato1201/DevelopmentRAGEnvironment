# 卒業研究・卒業論文執筆用メモ：既存サービスとの比較・研究としての新規性・開発を通じた発見と気づき

最終更新: 2026-09-22

## 0. このドキュメントの位置づけ

本ドキュメントは、`DevelopmentRAGEnvironment`配下で開発してきた一連のシステム（houdini21チュートリアル自動生成、Cloudflare RAG POC、ローカル/クラウド RAG基盤全般）について、卒業研究・卒業論文の執筆にあたって必要となる以下3点を整理したものである。

1. 従来のツール・AIを利用した既存サービスとの共通点・相違点
2. 研究としての新規性（何が新しく、何が新しくないかの誠実な切り分け）
3. 開発を進める中で得られた発見・気づき

技術的な実装詳細は他の設計ドキュメント（[content-generation.md](content-generation.md)、[houdini21-tutorial-gen-report.md](houdini21-tutorial-gen-report.md)、[cloudflare-rag-technical-report.md](cloudflare-rag-technical-report.md)、[cloudflare-rag-operations-manual.md](cloudflare-rag-operations-manual.md)）に譲り、本ドキュメントは「これらの実装が研究としてどう位置づけられるか」という一段上の視点に絞る。

## 2. 既存の従来型ツール・AIサービスとの比較

比較対象を4カテゴリに分け、それぞれとの共通点・相違点を整理する。

### 2.1 従来型ナレッジ管理ツール（Confluence / Notion / 社内Wiki / SharePoint等）

- **共通点**: ドキュメントを一箇所に集約し検索可能にするという目的は同じ。Notion自体も本システムのナレッジソースの1つとして利用している。
- **相違点**:
  - 従来型ツールは「人間が書いた文書を検索できるようにする」までが役割で、応答生成・要約・出典付き回答までは基本的に持たない（プラグイン追加で部分的に対応する製品はあるが標準機能ではない）。
  - 本システムは検索対象をJira／Backlog／カレンダー／地図情報にまで拡張し、かつハイブリッド検索・RAGによる生成応答・引用率などの品質指標まで自前で実装している点で踏み込みが深い。
  - 一方で、権限管理・全文検索エンジンの成熟度・UIの洗練度などは商用ツールに大きく劣る。ここは「検証環境・個人開発の技術検証」であるという前提を踏まえる必要がある。

### 2.2 AI企業アシスタント／コネクタ型サービス（Glean、Microsoft 365 Copilot、ChatGPT Enterprise + Connectors、NotebookLM等）

- **共通点**: 複数の異種データソース（チケット管理・カレンダー・ドキュメント）を横断的に検索し、LLMで要約・応答するという構成は同一。OAuthによるクリック接続で非エンジニアでも連携できるようにする、という設計思想も同じ方向を向いている。
- **相違点**:
  - これらの商用サービスは汎用オフィス業務・ナレッジワーカー向けであり、3DCGツール（Houdini）の内部状態を読み書きする「操作エージェント」は持たない。検索と応答生成が終着点であり、その先の「実際にツールを動かして検証する」機能は範囲外である。
  - 本システムはコスト管理・namespace予算・キー有効期限といったSaaS的な管理機能を、既製品を使わずスクラッチで実装している。この部分自体に技術的独自性はないが、「何が必要になるか」を実装しながら発見していくプロセス自体は教育的価値が大きい（§4で詳述）。
  - 商用サービスは大規模インフラの上に構築されているのに対し、本システムはCloudflare Workers + D1 + Vectorizeというサーバーレスの制約（サブリクエスト数・CPU時間・メモリ上限）の中で同等の機能を再現しようとしている点で、スケールも成熟度も大きく異なる。

### 2.3 AIコーディング／ツール操作エージェント（Cursor、GitHub Copilot Workspace、Blender向けAIアドオン、ComfyUI的ノードベースAIツール等）

- **共通点**: 自然言語の指示からツールを実際に操作し、成果物（コード・ノードグラフ）を生成するという点で、比較対象の中では最も近い。ツール呼び出し（tool use）のループでエージェントを動かす構成も共通。
- **相違点**:
  - 汎用コードエディタ向けのエージェントは、コンパイル・テストの成否という比較的明確な成功指標を持つ。一方Houdiniの手続き型ノードグラフは「cookエラーが出ない」ことと「意図した見た目になっている」ことの両方が必要で、後者はテキストだけでは検証できない。そのため本システムでは、ビューポートのスクリーンショットをエージェント自身に見せて視覚的に自己検証させる（`confirm_tutorial`）という、ドメイン固有の検証手段を実装した。
  - 汎用コーディングエージェントの「完了判定」は比較的単純だが、本システムでは「ノードを1つも作らずに終わろうとする」「下書きを提出したが確定していない」「ノードは作ったが提出関数を呼ばずに終わろうとする」という3種類の失敗モードを個別に検出し、それぞれに応じた救済ロジック（3段階レスキュー）を実装する必要があった。これはHoudini特有のツール呼び出し設計から生じた知見である。
  - Blender向けAIアドオンやComfyUI系のノードベースAIツールも「自然言語→ノード生成」という点は類似するが、生成結果を教材（Markdown＋動画）として書き出すところまで踏み込んでいる事例は一般的ではない。

### 2.4 Houdini特化型の学習リソース（SideFX公式チュートリアル、Entagma等の解説サイト、書籍、YouTube解説動画）

- **共通点**: Houdiniの操作方法を教える、という目的は同じ。
- **相違点**:
  - 静的コンテンツであり、個々の学習者の疑問やレベル、社内蓄積ノウハウ（houdini21DB等）に応じて動的に内容を変えることはできない。
  - 本システムは、RAG検索で組織固有の知見を踏まえたうえで、依頼ベースでオンデマンドにチュートリアル（実際に動作するノードグラフ付き）を生成し、さらに生成過程から解説動画まで自動生成する。「教材そのものを都度生成する」という点が最大の違いである。

### 2.5 比較のまとめ

| 観点 | 従来型ナレッジ管理 | AI企業アシスタント/コネクタ型 | AIコーディング/ツール操作エージェント | Houdini特化学習リソース | 本システム |
|---|---|---|---|---|---|
| 複数データソース横断検索 | △（限定的） | ○ | ✕ | ✕ | ○ |
| OAuthクリック接続によるノーコード連携 | △ | ○ | ✕ | ✕ | ○ |
| DCCツール内部の実操作・自己検証 | ✕ | ✕ | ○（汎用コード向け） | ✕ | ○（Houdini特化・視覚的自己検証あり） |
| 教材（文章＋動画）の自動生成 | ✕ | △（要約止まり） | ✕ | ✕（静的コンテンツ） | ○ |

## 3. 研究としての新規性

新規性は「要素技術としての新規性」と「システム統合・アーキテクチャとしての新規性」を分けて誠実に評価する。

### 3.1 要素技術としての新規性：低い（率直な評価）

本システムを構成する個々の技術要素は、いずれも既存のアルゴリズム・既存サービスの組み合わせである。

- ハイブリッド検索（ベクトル検索＋BM25のRRF融合）は既存手法。
- LLMのtool-useによるエージェントループも既存パターン。
- OAuth 2.0 Authorization Code Flowも標準仕様通りの実装。
- Cronベースの差分同期、サーバーレス環境でのバッチ継続処理パターンも、Cloudflare Workersのドキュメントに載っている設計指針の応用。
- 個々のサービス（RAGチャットボット、コーディングエージェント、動画生成ツール）は市場にすでに存在する。

したがって、「世の中にない技術を発明した」という意味での新規性を主張することはできない。この点は卒論で誇張せず、素直に認める必要がある。

### 3.2 システム統合・アーキテクチャとしての新規性

一方で、個々のサービスを**1つの一気通貫のフローとして統合した**点には、既存事例が見当たらない独自性がある。具体的には、以下の循環を1つのシステムの中で実現している。

> 知識を検索する（RAG） → 実際にツール（Houdini）の中で試してみる（操作エージェント） → その過程を教材として書き出す（チュートリアル自動生成） → 動画にする（解説動画自動生成） → 生成された教材が新たな知識としてまた検索対象になりうる

個別のサービスとして「RAGチャットボット」「コード/ノード生成エージェント」「動画生成ツール」はそれぞれ存在するが、これらをゲーム開発（Houdini）というドメインに特化させ、1つのパイプラインとして繋げた事例は一般に見当たらない。新規性はこの**統合・アーキテクチャのレベル**にあり、個々の要素技術のレベルにはない、というのが誠実な位置づけである。

さらに、この統合を「開発」「教育」「発展性」という3つの軸で捉えると、以下のような観察が得られる。

- **開発軸**: コード生成の自動テストに相当するものとして、「3DCGツールの操作結果をcookエラーの有無と視覚的な見た目の両方で自己検証する」というパターンを実装できた。これは一般的なコード生成エージェントの検証手法（コンパイル・単体テスト）をそのまま流用できない、DCCツール特有の課題に対する具体的な解の1つになっている。
- **教育軸**: チュートリアルが「読む」だけでなく「実際に動くノードグラフ」を伴い、さらに生成過程のスクリーンショットを解説動画に変換することで、初学者への説明コストを下げられる可能性が確認できた。教材の生成コストそのものを下げることで、少人数チームや個人でも継続的な教育コンテンツ整備が可能になるという示唆がある。
- **発展性軸**: 同じRAG基盤（Cloudflare Workers版）にJira／Backlog／カレンダー／地図情報など、ゲーム開発に直接関係しない情報源まで統合できたことから、Houdini特化ツールとして閉じずに、周辺の開発管理・組織運用情報まで横断検索できる汎用ナレッジ基盤への発展可能性が見えた。これは当初想定していなかった副次的な発見である。

### 3.3 開発者自身の所感（そのまま記録）

本人の言葉で以下のように総括している。これは卒論の「考察」節で、研究の位置づけを誠実に示す材料として活用できる。

> 一個一個のサービスだけならあるが、それらを一つにしたものはないので、それら全体を通してのフローや開発・教育・発展性という面では発見があったのではないか。基本的には世に出ている技術・既存のアルゴリズムを利用し、組み合わせて、積み上げてきたものなので、新規的な発見があったのかというと微妙だが、個人の知見という意味では発見や気づきは多かった。

この所感は§3.1〜3.2の評価と一致しており、「要素技術としては新規性が薄いが、統合・フロー・教育・発展性という観点での知見は独自」というスタンスが、この研究の最も誠実で説得力のあるまとめ方だと考えられる。

## 4. 開発を通じた発見・気づき

実装・デバッグ・リファクタリングの過程で得られた気づきを4カテゴリに整理する。いずれも本プロジェクトの実際の開発ログ（バグ修正・機能追加の履歴）に基づく具体的な知見である。

### 4.1 技術的発見

- **エージェントの「完了」判定は1段階では不十分**。単純に「ツール呼び出しが止まったら完了」とすると、(1)何も作らずに終わる、(2)下書きを提出したが確定していない、(3)ノードは作ったが提出関数を呼ばずに終わる、という複数の失敗モードが発生する。失敗モードごとに異なる救済メッセージを送る3段階レスキューロジックが必要だった。
- **例外の握りつぶしは「虚偽の成功報告」を誘発する**。`except Exception: pass`のような実装は、ツール実行結果に例外の痕跡が残らず、エージェントに「成功したように見えるが実際は失敗している」情報を渡してしまう。ツール結果は例外の有無を明示的にエージェントへ伝える必要がある。
- **DCCツール内への重量級embeddedウィジェットの組み込みはリスクが高い**。QtWebEngineのような重量級コンポーネントをHoudiniのPythonパネル内に埋め込むと、GPUコンテキストの競合等でパネル全体がフリーズしうる。外部プロセス（OSの標準プレイヤー等）に処理を委譲する設計の方が、DCCツール向けアドオンでは安全という知見。
- **サーバーレス環境のバッチ処理は「クライアント駆動の継続処理」に収束する**。Cloudflare Workersのようにサブリクエスト数・CPU時間・メモリに強い制約がある環境では、`opId`＋`startIndex`／`batchSize`／`nextIndex`のような、クライアント側がポーリングしながら処理を継続させる設計パターンが実用上必須になる。
- **多重にネストした文字列エスケープはソースコードの目視・静的チェックでは検出できない**。外側のテンプレートリテラルの中にさらに別言語の文字列リテラルを埋め込む構成（TSのテンプレートリテラルの中にJSのコードを文字列として持つ等）では、`\n`と`\\n`の違いのようなエスケープミスがビルド時に静的解析をすり抜け、本番でのみ顕在化する。**実際にビルド・実行して得られる「本当の出力」を検証する**（esbuildでバンドルして実際のJSを取り出しnode --checkする等）以外に、確実な検出方法がないと分かった。

### 4.2 エージェント設計における発見

- **制限への到達は「急停止」より「猶予を与えた優雅な収束」の方が成功率とUXの両方で優れる**。イテレーション数・コスト上限に近づいた際、即座に打ち切るのではなく、「あと1回で完了させてください」という猶予（grace nudge）を挟むことで、無駄な失敗を減らせる。
- **DCCツール操作エージェントには、コード生成エージェント以上に「実行結果の可視化」が信頼性確保に効く**。コードは差分を読めば検証できるが、ノードグラフの見た目の妥当性はテキストログだけでは判断できない。ビューポートスクリーンショットによる視覚的自己検証は、この種のエージェントに固有の必須要素だと分かった。
- **安全装置は「実行経路ごとに個別に効かせる」必要がある**。手動保存パス（確認ダイアログあり）にのみ実装した安全チェック（未完了時の動画生成スキップ）が、自動保存パス（chainモード）には存在しないという抜け漏れが実際に発生した。1つの安全装置を追加したら、その装置が効くべき全ての実行経路を洗い出して確認する、という開発上の教訓を得た。

### 4.3 UX／プロダクト設計における発見

- **非IT系ユーザーにとって、API keyやOAuthクライアントIDの手動発行そのものが導入障壁になる**。機能を増やすことよりも、「接続」ボタン1つで連携が完了するように導入コストを下げることの方が、実際の利用率に対するインパクトが大きいと考えられる。
- **管理画面のごく小さなミス（1文字のエスケープ漏れ）が管理UI全体を機能停止させうる**。本番影響の検証は「変更した箇所」だけでなく、「その変更が実際にどう配信されるか」まで含めて確認する体制が必要だと痛感した。
- **利用者向けの機能（連携タブなど）は、実装が完了しても「デプロイして初めて使える」**。実装済みだが未デプロイの機能について、利用者から「見当たらない」という指摘を受けたことで、開発と運用の間のギャップを可視化する重要性を再認識した。

### 4.4 開発プロセスにおける発見

- **「不備の洗い出し→修正→追加機能の提案→順番に実装」という小さな反復サイクルは、一度に大きく作るより手戻りが少ない**。リファクタリング依頼のたびにこのサイクルを回したことで、複数の潜在バグ（KB概要の反映漏れ、リトライ機能の実質未実装、エラーメッセージの分かりにくさ等）を早期に発見できた。
- **ドキュメントを都度更新し続けることで、後から実装意図を追いやすくなる**。技術レポート・運用マニュアル・機能対応表を実装の都度更新したことで、本ドキュメントのような後からの振り返り・研究としての整理作業のコストが大幅に下がった。
- **個人開発でも「実装→検証→ドキュメント化」の3点セットを省略しないことが、後工程（卒論執筆等）でのmaterial再構成コストを大きく下げる**。これは本ドキュメント自体が、その効果を実証する具体例になっている。

## 5. 卒論構成への活用方針（メモ）

- 第2章「関連研究・既存サービス」 ← §2の比較表・各カテゴリの記述

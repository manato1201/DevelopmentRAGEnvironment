## 1. 全体像

検索は、`src/retrieve.ts` の `retrieve()` が**指揮者**で、図11の 7〜9 に当たります。

[![リクエストの一生](../../images/11-request-life.svg)](../../images/11-request-life.svg)

```
質問 ──▶ ① HyDE（仮の回答を作る）            hydeExpand       …… embeddings.ts
        ② 2本のベクトルを作る                 embedText ×2     …… 仮の回答 と 質問そのもの
```

## 2. 基礎

### 2.1 分割（チャンク）

第11回の `chunkText`（1000文字・150重ね）。**登録時に1度だけ**行います。サイズの選び方は、トレードオフです。

| 大きくすると | 小さくすると |
|---|---|
| 文脈が長く残る | 検索が、狙った箇所に当たりやすい |
| 1チャンクに複数の話題が混ざり、ベクトルが「平均」になって当たりにくい | 前後の説明が欠け、回答の材料が足りない |
| 回答のプロンプトが長くなり、トークン（費用）が増える | チャンク数が増え、埋め込みの費用と保存量が増える |

### 2.2 ベクトルと類似度

**埋め込み（embedding）**は、文を**768個の数（ベクトル）**に変える処理です（`OUTPUT_DIMENSIONALITY = 768`。Vectorize のインデックスの次元と**必ず一致**させる）。意味が近い文は、ベクトルの向きが近くなります。

**コサイン類似度**＝2つのベクトルの向きの近さ（-1〜1）。

```
cos(a, b) = (a・b) / (|a| × |b|)        a・b は内積（対応する要素の積の合計）
```

- 先に**長さ1に直して**（正規化）おけば、`|a| = |b| = 1` なので、**内積だけ**で済みます。`graph.ts` の `normalized()` と `dot()` がこれ（第14回）。
- 検索では、Vectorize が**近い順に**返します（自分で計算しない）。

**小さな例（2次元）:** `a = (1, 0)`、`b = (0.6, 0.8)`（長さ1）。内積 = 0.6。`c = (0, 1)` とは内積 0（直交＝無関係）。`a` と同じ向きなら 1。

### 2.3 単語検索：BM25 と FTS5（trigram）

**BM25** は、「その単語が、そのチャンクに**多く**出るほど高く、**どのチャンクにも出る**ありふれた語ほど低く」するスコアの式です（細かい式は覚えなくてよい）。SQLite の **FTS5** は、これを `ORDER BY rank` で返します（`rank` が小さいほど良い＝上位）。

このプロジェクトの FTS5 は `tokenize = 'trigram'`（`migrations/0002_fts.sql`）。**3文字ずつ**に区切る方式で、**日本語の分かち書きが要らない**（「ノード」「ネットワーク」を部分一致で見つけられる）代わりに、**2文字以下の語は一致しません**（SQLite の仕様）。

**検索語の安全化（`escapeFtsQuery`）:** FTS5 の `MATCH` は、`-`・`:`・`"`・`( )`・`AND/OR/NOT` を**命令**として読みます。質問をそのまま渡すと `fts5: syntax error` で検索全体が失敗します（2026-09-04 に実際に起きた）。そこで、**空白で区切った語を1つずつ `"` で囲む**。

| 入力（質問） | 渡す `MATCH` |
|---|---|
| `-fフラグの直し方` | `"-fフラグの直し方"` |
| `比率: 3:1` | `"比率:" "3:1"` |
| `say "hi"` | `"say" """hi"""`（中の `"` は `""` に） |

語の間は空白のまま＝FTS5 の既定の「**語ごとの AND**」の意味は保たれます。

### 2.4 RRF（Reciprocal Rank Fusion）：順位を合わせる

ベクトルの類似度（0.7 など）と BM25 のスコア（-8.3 など）は、**目盛りが違う**ので足せません。そこで**順位だけ**を使います。

```
各リストでの順位 r（0始まり）に対して   寄与 = 1 / (k + r + 1)        k = 60
チャンクの得点 = 登場したリストすべての寄与の合計
```

**`k = 60`** は一般的な既定値。1位と2位の差が極端にならないようにする係数です（`k` が大きいほど、順位の差が効かなくなる）。

**手計算の例（実測と一致を確認済み）:** 3本のリスト（ベクトル1、ベクトル2、単語検索）が次のとき。

| リスト | 1位 | 2位 | 3位 |
|---|---|---|---|
| ベクトル1（HyDE） | a | b | c |
| ベクトル2（質問そのもの） | b | a | d |
| 単語検索 | c | b | — |

| チャンク | 寄与の内訳 | 合計 |
|---|---|---|
| **b** | 1/62（V1:2位）+ 1/61（V2:1位）+ 1/62（単語:2位） | **0.04865** |
| **a** | 1/61（V1:1位）+ 1/62（V2:2位） | **0.03252** |
| **c** | 1/63（V1:3位）+ 1/61（単語:1位） | **0.03227** |
| **d** | 1/63（V2:3位） | **0.01587** |

結果の順位は **b → a → c → d**。読み取れること:

- **どのリストでも上位の `b`** が1位。「複数の方式が同意するもの」が強い（RRF の狙い）。
- **単語検索で1位の `c`** は、ベクトルでは3位なので、`a` に僅差で負ける。
- 得点の**絶対値に意味はない**（理論上の最大は、3本とも1位で `3/61 ≈ 0.0492`）。だから画面の「関連度」は、**最高点を100とした割合**にする（`buildContextTexts`）。上の例なら b=100、a=67、c=66、d=33。

### 2.5 HyDE：質問ではなく「仮の答え」で探す

質問文（「煙が消えない」）と、ドキュメントの文（「dissipationを上げる」）は、**言い回しが離れて**います。そこで、**まず LLM に「こう答えるだろう」という短い仮の説明を書かせ**、それを埋め込みます（`hydeExpand`）。答えの文は、ドキュメントの文に近いからです。

このプロジェクトの工夫（2026-10-21）:

1. **温度 0**（`temperature: 0`）。同じ質問から**毎回ほぼ同じ**仮の回答を作り、検索結果が実行のたびにぶれるのを抑える。
2. **質問そのものも、もう1本のベクトルとして使う。** 仮の回答が1つの章（SOP など）に決め打ちしても、質問そのものの検索が**安定させる**。
3. 質問に章が無いときは、「どれか1つに決めつけず、一般的な言い方で」と指示する。

### 2.6 並べ替えと間引き

**(a) 取る件数の計算**

```
retrieve(limit = 8) ──▶ hybridSearch(limit = 8 × 3 = 24)
hybridSearch の中:   topK = min(24 × 3, 50) = 50     ← Vectorize の上限が50（returnMetadata:"all" のとき）
最後に rrfMerge(...).slice(0, 24)
```

**多めに取って、後で絞る**（レベル・章・namespace の絞り込みで減るため）。以前は**3倍を二重に**かけて `topK` が上限を超え、`VECTOR_QUERY_ERROR (40025)` になった（コメントに記録）。**`Math.min(…, 50)` の「上限で止める」書き方が、その再発防止**です。

**(b) 章の指定があれば先に並べる（`boostByContext`）**

質問に「SOP で」とあるとき、見出し `【Houdini 22 / SOP / transform】` を持つチャンクを**前に**、それ以外を後ろに置きます（**除外はしない**）。

```ts
for (const chunk of ranked) {
  const header = parseHeader(chunk.metadata.text);
  (header !== null && contexts.includes(header.context) ? hits : rest).push(chunk);
}
return [...hits, ...rest];          // それぞれの中の順は、元の順位のまま
```

これは**安定な分割（partition）**です。実測:

| 入力の順（元の順位） | `SOP` を指定した結果 |
|---|---|
| ① VOP/transform ② SOP/transform ③ SOP/merge ④ 見出しなし | ② SOP/transform → ③ SOP/merge → ① VOP/transform → ④ 見出しなし |

> **なぜ「点数を掛ける」方式にしないのか:** 点数を1.5倍にする方式では、**順位が離れた正解**（ベクトル3位だけに出た SOP）を、すでに上位にいる別の章の上へ動かせない。**並べ方で決める**ほうが、結果が予測できる（コメントの趣旨）。

**(c) 章の指定の検出（`detectContextCues`）**

正規表現で、`SOP`・`VOP`・`APEX`… を**英字の単語として**探します（前後が英字でないとき）。実測: 「SOPで transform を…」→ `SOP`、「一番 top にある」→ **なし**（`TOP` は、**大文字だけ**に反応。普通の英単語 top を避けるため）、「TOPで PDG」→ `TOP`。

**(d) 同名ノードの注意書き（`ambiguityNote`）**

章の指定が無く、同名のノードが複数の章に出たとき、**既定の章（SOP 優先）で答え、他の章があることを1行添える**よう、プロンプトに注意書きを足します。実測の出力:

> 注意（章の曖昧さ）: 「transform」は SOP / VOP にあります（既定: SOP）。…

**(e) namespace ごとの間引き（`capPerNamespace`）**

複数のDBを横断したとき、無関係なDBのチャンクが**偶然高得点**で紛れ込んで、結果を圧迫することがあります。**スコア順を保ったまま**、namespace ごとの上限を超えた分だけ捨てます。

| 順位 | namespace | その namespace の件数（採用前） | 上限 2 のとき |
|---|---|---|---|
| 1 | A | 0 | 採用（A=1） |
| 2 | A | 1 | 採用（A=2） |
| 3 | A | 2 | **捨てる** |
| 4 | B | 0 | 採用（B=1） |

上限は `namespaces.result_limit`（D1）で namespace ごとに決め、無ければ呼び出し時の `limit`。

## 3. このプロジェクトでは：2層の「個人／共有」と検索

- **共有**は `VEC_SHARED`、**個人**は `VEC_PERSONAL`（別のインデックス＝**物理分離**）。`splitNamespacesByScope` で振り分けてから、**個人は `owner_user_id = 本人` で絞って**引く（`hybrid.ts`）。
- ベクトルのリストは、**共有の結果の後ろに個人の結果をつなげる**だけ（類似度で混ぜ直さない）。BM25 も同じ。つまり、**個人のナレッジは、同じ検索の中で、共有より後ろに並びやすい**。意図した挙動か、将来、見直す候補か、**判断するのは保守する人**です。
- 4つの検索（共有ベクトル・共有BM25・個人ベクトル・個人BM25）は独立なので、`Promise.all` で**並列**に実行（逐次だと待ち時間が足し算になっていた不備の修正）。

## 4. 調整のつまみと、触る前の確認

| つまみ | 場所 | 変えるとどうなる | 変える前に |
|---|---|---|---|
| チャンクの大きさ・重ね | `chunking.ts` の既定 | **再登録が必要**（既存は古いまま） | 再登録の費用、テスト `crawl_*` |
| `k = 60` | `hybrid.ts` `rrfMerge` | 順位の差の効き方 | 検索の評価セットを作ってから |
| `topK` の上限 50 | `hybrid.ts` | Vectorize の仕様上限 | 公式の仕様を確認 |
| 取る件数 `limit × 3` | `retrieve.ts` | 絞り込みで減る分の余裕 | 遅延と費用 |
| ベクトルの次元 768 | `embeddings.ts` | **インデックスの作り直し** | ほぼ変えない |
| namespace の上限 | D1 `namespaces.result_limit` | 横断検索の偏り | 管理画面で変更できる |

## 6. つまずきやすい点

- **「ベクトル検索だけで十分」と考える。** 固有名詞・コード片は、**単語検索のほうが強い**。だから両方を使う。
- **RRF の得点を、確率や割合として読む。** 絶対値に意味は無い。
- **チャンクの設定を変えて、既存データの挙動が変わらない。** 再登録するまで、古い切り方のまま。
- **2文字の語で、単語検索が空になる。** trigram の仕様。ベクトル検索が補う。
- **個人のナレッジが出てこない。** 許可された namespace（`allowedNamespaces`）と、`owner_user_id` の一致を確認（第5回）。

## 7. 確認問題

1. BM25 のスコアとベクトル類似度を、足さずに RRF を使う理由は？
2. `escapeFtsQuery` が無いと、どんな質問で、何が起きる？
3. HyDE に温度 0 を指定する理由は？
4. `boostByContext` が「除外」ではなく「前に並べる」理由は？
5. `topK = min(limit × 3, 50)` の `50` は何の上限か。

## 解答の方針

- 演習 12.1: x = 1/61 + 1/63 = 0.03227、y = 1/62 + 1/61 = 0.03252、z = 1/63 + 1/62 + 1/61 = 0.04839。順位は **z → y → x**。
- 演習 12.4: `hybridSearch` の `limit = 60`、`topK = min(180, 50) = 50`。`rrfMerge` の結果を 60 件に切る（実際の候補は、リストの合計までなので、それ以下）。最終的な返却は `limit = 20` 件まで。
- 演習 12.5: ①質問から `detectContextCues` が `SOP` を検出したか → ②チャンクの本文の先頭に見出し（`【Houdini … / SOP / …】`）があるか（旧形式の登録は無い＝`hasHeader`）→ ③`capPerNamespace` で落ちていないか → ④再クロール。
- 確認問題 5: Vectorize が `returnMetadata: "all"` のときに返せる件数の上限。

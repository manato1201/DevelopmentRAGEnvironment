2.1 4種類のテスト

種類 何を確かめるか 速さ 実行
型検査 型の食い違い（tsc） 数秒 cd cloudflare-rag-poc; npm run typecheck
純関数・ハンドラ（Worker） ルールと、D1 の読み書き（偽の D1・本物の表） 数秒〜十数秒 npm test（25ファイル）
単体テスト（Houdini 側） 画面に依存しない部品 約20秒 uv run python -m unittest discover -s houdini/tests
通しの確認（hython） 画面の結びつけ（ボタン → 関数 → 通信） 数秒 hython houdini/tests/smoke_*.py（QT_QPA_PLATFORM=offscreen）

どれも、本番には、つながりません。 偽の D1（node:sqlite）・偽の外部 API・偽のサーバーを使います。

画面の <script>（chatUi.ts）は、型検査では守れません。ui_syntax.test.mjs が、構文を読んで確かめます（第7回）。

2.2 本番を変える操作（見分ける）

操作 本番を変える？ 戻せる？
npm test・npm run typecheck いいえ —
wrangler d1 migrations list … --remote いいえ（一覧だけ） —
wrangler d1 execute … --remote --command "SELECT …" いいえ（読むだけ） —
wrangler d1 migrations apply … --remote はい 自動では戻らない（打ち消す SQL を、新しいマイグレーションとして足す）
wrangler deploy はい wrangler rollback（直前の版へ）
wrangler secret put はい 前の値は見えないので、控えておく
git push リポジトリを変える git revert（新しいコミットで打ち消す）
deploy_panels.py 自分の PC のコピーを変える 自動バックアップから戻す

ルール: 本番を変える操作は、人が、操作の名前を挙げて、許可してから行う。 自動の道具やAIも、勝手に進めない。許可は、その操作ごと（前の許可は、次に持ち越さない）。

2.3 順序の理由

  1. 型検査 → テスト → 通しの確認（手元で、壊れていないことを確かめる）。
  2. D1 のマイグレーション（本番）→ Worker のデプロイ。表の形が先。新しい Worker が、まだ無い列を読むと、失敗する。
  3. 疎通の確認: 鍵なしで、新しい API を呼び、401（認証が効いている＝窓口がある）。404 なら、Worker が古い。
  4. パネルの配置は、Worker のあと。先に配ると、新しい機能が「サーバーが、この機能にまだ対応していません」（404）になる。
  5. ドキュメント → コミット・プッシュ。実際に出した内容と同じ版を記録する。

2.4 戻し方

症状 戻し方
デプロイした Worker が、おかしい cd cloudflare-rag-poc; npx wrangler rollback（直前の版へ。D1 は、そのまま）
マイグレーションが、おかしい 新しいマイグレーションで、打ち消す（例: 追加した列を ALTER TABLE … DROP COLUMN、索引を作り直す）。データを消す変更は、事前に /admin/backup/export で退避
配置したパネルが、おかしい deploy_panels.py が作る python_panels_backup_<日時> から、コピーし戻す。再起動
間違えてコミットした（秘密・不要なファイル） 秘密なら、その鍵を失効して作り直す（履歴から消しても、遅い）。不要なファイルは、git rm --cached

2.5 日々の見守り

運営者手順書 §4・06 保守の手順 §1 の点検の要点:

  • 毎日: 管理画面の「利用状況・コスト」で、費用の急な増加・429・500 が無いか。
  • 毎週: npx wrangler d1 insights rag-poc-db --timePeriod 7d で、読み取り行数が突出した SQL が無いか（2026-10-16 の事故の再発防止）。
  • 毎月: 設定バックアップのエクスポート・使っていない鍵の失効・依存の更新確認。
  • 自動: Cron（30分ごとのヘルスチェック。異常ならアラート通知）。

2.6 費用と上限

  • Workers Paid（月 $5〜）。D1 の読み取り・書き込みの行数、Vectorize の次元数、AI の API 料金（トークン）が、費用の中心。
  • 鍵ごとの予算（token_budgets）で、使いすぎを止める（第4回）。上限に達すると、実行の前に止まる（429）。
  • 数字は変わる。cost-and-quota.md と、公式ページで確認する（2026-10時点）。

2.7 Git の作法

  • コミットメッセージ: そのリポジトリの git log の書き方に合わせる（このリポジトリは、英語の短い説明＋必要なら箇条書き）。
  • ファイルを、名前で指定してステージする（git add <ファイル>）。git add -A は使わない（local-chat/ などの、入れないものまで入るため）。
  • 秘密（鍵・トークン）を、コミットしない。チャットにも貼らない。
  • コミット・プッシュ・デプロイは、頼まれたときだけ。

3. このプロジェクトでは

  • 標準の流れは 図16。運営者の手順は operator-runbook.md §6（6.1 に、課題の機能を出すときの手順）。
  • 実際に、順序を取り違えた事例: パネルを先に配り、Worker が古かったため、「課題」タブが「未対応」になった（2026-10-28。第10回）。その後、friendly_error に、「サーバーが、この機能にまだ対応していません」の文言を足した。

演習 9.2（見分ける） 次の操作を、「本番を変えない／変える（戻せる）／変える（戻せない）」に分けてください。(a) wrangler d1 migrations list … --remote (b) wrangler d1 migrations apply … --remote (c) wrangler deploy (d) wrangler rollback (e) git push (f) wrangler d1 execute … --remote --command "UPDATE …"

5. つまずきやすい点

  • 「テストが通った = 本番で動く」と思う。 偽の D1・偽のサーバーでの結果。本番の疎通（401・実機）は、別に確かめる。
  • マイグレーションを、一覧せずに適用する。 保留中のものが、他にもあるかもしれない。
  • デプロイしたのに、変わらない。 npx wrangler deploy の出力の「Current Version ID」を確かめる。別のフォルダで実行していないか。
  • 許可を、持ち越す。 前に許可した操作を、次も許可されたと思わない。

6. 確認問題

  1. 型検査とテストが通っても、本番を確かめる理由は？
  2. D1 → Worker → パネルの順にする理由を、それぞれ言え。
  3. wrangler rollback で、戻らないものは？
  4. git add -A を使わない理由は？
  5. 毎週 d1 insights を見る理由は？

解答の方針

  • 9.2: (a) 変えない (b) 変える（戻せない） (c) 変える（戻せる） (d) 変える（戻す操作） (e) リポジトリを変える (f) 変える（戻せない。事前に退避）。
  • 9.3: 差分があれば、「直したのに実機で変わらない」の原因。--pypanel で配置して、再起動。
  • 確認問題 3: D1 のデータ・マイグレーション（表の形）。
  • 確認問題 5: 読み取り行数が突出した SQL（全件走査）を、早く見つけるため（2026-10-16 の事故）。

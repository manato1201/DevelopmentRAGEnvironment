## 2. 基礎

### 2.1 アルゴリズムを「読む」手順

どんな関数も、次の4歩で読めます。

1. **入力と出力を書く。**（型・範囲・空のとき）
2. **小さい具体例を1つ決める。**（大きすぎず、境界を含む数）
3. **1行ずつ、変数の値を表に書く。**（これが**トレース表**）
4. **出力が、期待と合うか確かめ、合わない行を探す。**

> コードを読むだけで分かった気になるのが、一番の落とし穴です。**必ず数を入れる。**

### 2.2 トレース表の例：`chunkText`（スライディングウィンドウ）

`src/chunking.ts` の `chunkText(text, size = 1000, overlap = 150)` は、長い文を**重なりつきで切り分けます**。入力を「2500文字」にして追います。

| 周 | `start` | `end = min(start+size, 2500)` | 切り出す範囲 | 長さ | `end >= 2500`? | 次の `start = end - overlap` |
|---|---|---|---|---|---|---|
| 1 | 0 | 1000 | [0, 1000) | 1000 | いいえ | 850 |
| 2 | 850 | 1850 | [850, 1850) | 1000 | いいえ | 1700 |
| 3 | 1700 | 2500 | [1700, 2500) | **800** | **はい → break** | — |

結果は **3個**（長さ 1000・1000・800）。実際に動かすと `chunks 3 [1000, 1000, 800]`、開始位置は `[0, 850, 1700]` で、表と一致します。

**なぜ重ねる（overlap）のか:** 文の途中で切ると、切れ目の前後に**意味が分かれて**しまい、検索で見つかりにくくなります。150文字を重ねて、**切れ目をまたぐ話題を、どちらかのチャンクに丸ごと入れる**ためです。

**不変条件（invariant）— 壊れる条件を言えるか:**

- 次の `start` は `end - overlap = start + size - overlap`。**`size > overlap` のときだけ、`start` が毎周前に進む。**
- `overlap >= size` にすると、`start` が進まない（または戻る）ので、**無限ループ**になります。既定値（1000 / 150）では起きませんが、**引数を変える人（将来のあなた）は知っておく**こと。
- 入力が空（`trim` 後に長さ0）なら `[]`、`size` 以下なら1個だけ。**境界の2つの特別扱いが、冒頭の2行**です。

### 2.3 計算量（どれくらい重いか）

**計算量**は、「入力が n 倍になると、手間が何倍になるか」の目安です。

| 記法 | 意味 | 例 |
|---|---|---|
| O(1) | 入力に関係なく一定 | `Map.get`、`Set.has` |
| O(n) | n に比例 | 配列を1回なめる（`for`） |
| O(n log n) | n より少し重い | 並べ替え（`sort`） |
| O(n²) | n の2乗 | 配列の全ペアを比べる（二重 `for`） |

**このプロジェクトの実例（第14回）:** グラフ画面の「似ている文書を線で結ぶ」処理（`graph.ts`）は、全ノードの**全ペア**で内積を取る O(N²) です。

- ノード数 N = 500、ベクトルの次元 d = 768。
- 比べる回数: `500 × 499 = 249,500` 回（`i` と `j` の二重ループ）。
- 掛け算の回数: `249,500 × 768 ≈ 1.9億` 回。
- ノードが2倍の1000になれば**4倍（約7.7億回）**。コードのコメントに「1000では描画・計算に時間がかかるようになったため、上限を500にした」とあるのは、これが理由です。

> **設計の教訓:** 計算量が n² のものは、**n に上限を付ける**のが一番簡単で確実な対策です（`MAX_GRAPH_NODES = 500`）。

### 2.4 データ構造：配列・Map・Set の使い分け

| 道具 | 向いている用途 | このプロジェクトの例 |
|---|---|---|
| 配列 `[]` | 順序が大事 | 検索結果の順位（`RankedChunk[]`） |
| `Map<キー, 値>` | キーで**速く**引く・集計する | `scoreById`（RRF の合計点）、`counts`（namespace ごとの件数） |
| `Set<値>` | 「もう見た？」の判定、重複除去 | `seen`（エッジの重複）、`present`（回答に出た用語） |

**`Array.includes` と `Set.has` の違い:** 配列の中から探すのは O(n)、`Set` は O(1)。`for` の中で毎回探すと、全体が O(n²) になります。`graph.ts` のエッジの重複判定は `Set` なので、500ノードでも軽い。

**「向きのないペア」を1つにまとめる技（`graph.ts`）:** `a` と `b` のエッジは、`(a,b)` でも `(b,a)` でも同じ線です。そこで、**文字列の小さいほうを先にしたキー**を作ります。

```ts
const key = a < s.id ? `${a}|${s.id}` : `${s.id}|${a}`;   // どちらの向きで来ても同じキーになる
if (seen.has(key)) continue;
seen.add(key);
```

### 2.5 並べ替え：安定ソートと「決め手」

JavaScript の `Array.prototype.sort` は、**安定ソート**です（同じ値の並びは、元の順を保つ）。それでも `listSort.ts` が元の位置（`index`）を持ち回すのは、**「同点のときの順序を、コードで保証する」**ため（読む人に意図が伝わり、環境にも依存しない）。

`sortItems`（`src/listSort.ts`）の考え方：

1. `{ item, index }` に包んで、元の位置を覚える。
2. 比較は**複数の「決め手」を順に**見る（`spec` の配列）。先頭が主キー（昇順・降順を選べる）、2番目以降は同点のときの決め手（常に昇順）。
3. すべて同点なら `x.index - y.index`（元の順）。
4. **空の値（null・空文字・`-`・NaN）は、昇順でも降順でも、いちばん後ろ。** 降順で `c * direction` を掛けても、空の扱いだけは**掛けない**（先に `return` している）のがポイント。

**例（`sortedRowOrder`）:** 表の「利用回数」列を降順にする。セルが `["12","3","-","1,234 件"]` なら、`parseCellValue` が `"1,234 件"` を数 1234 と読み（カンマを除き、後ろの単位を許す正規表現）、`"-"` は `empty`。結果の並びは **1234 → 12 → 3 → 空** になります。

**文字の比較は `Intl.Collator("ja", { numeric: true })`:** `"課題2"` と `"課題10"` を、**数として** 2 < 10 に並べます（普通の文字比較だと `"10" < "2"` になる）。

### 2.6 純関数と、乱数を使わない「乱数」

**純関数**＝同じ入力なら必ず同じ出力で、外の状態（時刻・DB・ネットワーク）を読み書きしない関数。**テストが簡単**で、**画面とテストが同じコード**を使えます（第7回）。

`asciiArt.ts` の `cellDelay(x, y)` は、マスごとの「遅れ」を作る**擬似乱数**ですが、乱数関数（`Math.random`）を使いません。

```js
function cellDelay(x, y) {
  const n = Math.sin(x * 12.9898 + y * 78.233) * 43758.5453;
  return n - Math.floor(n);          // 小数部だけ取り出す → 0以上1未満
}
```

- `sin` の値は -1〜1。それに大きな数を掛けて**小数部だけ**取ると、座標がわずかに違うだけで値が大きく変わる（**ハッシュ**のような振る舞い）。
- **同じ座標なら、いつも同じ値**。だから、アニメーションの各コマが**再現できる**し、テストで検証できる。
- この定数（12.9898・78.233・43758.5453）は、シェーダーでよく使われる慣用句です。**意味を理解する必要はなく、「座標から0〜1を決める関数」として使う。**

### 2.7 正規表現の部品：先読み・後読み

`glossary.ts` と `houdiniContext.ts` は、**単語の境界**を `(?<![a-z0-9_])` と `(?![a-z0-9_])` で作ります。

| 部品 | 意味 |
|---|---|
| `(?<!X)` | 直前が X **でない**（後読みの否定） |
| `(?!X)` | 直後が X **でない**（先読みの否定） |

`"top"` を探すとき、`stop`・`laptop` に反応しないよう、**前後が英数字でないとき**だけ一致にします。日本語（`ノード`）は単語の区切りが無いので、そのまま含まれていれば一致。

**注意:** ユーザーの入力を正規表現に入れるときは、`escapeRegExp` で記号をエスケープする（`glossary.ts`）。そうしないと、`C++` のような語が構文エラーや誤一致になります。

## 3. このプロジェクトでは：用語の数え上げ（`findTerms`）を読む

`src/glossary.ts` の `findTerms(text)` は、質問文に出てくる Houdini の用語を**重複なしで**返します。ポイントは**二重カウントの防止**です。

- 辞書に `Attribute Wrangle` と `アトリビュート`（別名に `attribute`）がある。
- 質問が「**Attribute Wrangle** で **attribute** を作る」なら、前半の `attribute`（Wrangle の一部）は数えず、後半の単独の `attribute` だけを数えたい。

アルゴリズム：

1. 全用語・全別名で、一致する**範囲（start, end）**を全部集める（`spans`）。
2. ある範囲 a が、**別の用語の、より長い範囲 b にすっぽり含まれる**なら、a を捨てる。
   `b.start <= a.start && b.end >= a.end && b の長さ > a の長さ && b.term !== a.term`
3. 残った用語を、辞書の順で返す。

実行結果（実測）:

| 入力 | 出力 | 読み方 |
|---|---|---|
| `Attribute Wrangle で attribute を作る。top の話ではない。TOP ネットワークは?` | `ネットワーク` / `アトリビュート` / `Attribute Wrangle` | 単独の `attribute` は `アトリビュート` として1回。Wrangle の中の `attribute` は数えない。`top` には反応しない（境界の指定が効いている） |
| `copy to points で scatter した点にVEXを` | `Scatter` / `Copy to Points` / `VEX` | 辞書の順（`Scatter` が先）で返る |

> 3行目の入力の `TOP ネットワーク` は、辞書の別名が `topネットワーク`（空白なし）なので `PDG` には**一致しません**（`ネットワーク` だけが数えられる）。辞書の別名は**書いた綴りのとおりにしか一致しない**ので、足りない言い方は、`glossary.ts` に1行足します。

**計算量:** 用語数 T × 別名数 × 文章の長さ。辞書は約90語・質問は短いので問題なし。**辞書を数千語にするなら、別の方法（Aho–Corasick など）が必要**になります（今は不要。足すときに考える）。

## 5. つまずきやすい点

- **トレースを省く。** 「読んで分かった」は、たいてい間違い。数を入れる。
- **`slice(a, b)` の `b` は含まれない。** `[a, b)`（右は開区間）。`chunkText` のトレース表の「範囲」も同じ。
- **`sort()` に比較関数を渡さない。** 数値は**文字として**並ぶ（`[10, 2, 1].sort()` → `[1, 10, 2]`）。
- **`Math.round` と小数の誤差。** `0.1 + 0.2` は `0.30000000000000004`。表示や保存の前に、`Math.round(x * 1000) / 1000` のように丸める（`mistakeScore` がそう）。
- **ミリ秒と秒の混同。** `Date.now()` はミリ秒、D1 に入れる `created_at` は**秒**（`Math.floor(Date.now() / 1000)`）。

## 6. 確認問題

1. `chunkText` で、チャンク数が `ceil((n - overlap) / (size - overlap))` になる理由を説明せよ（n=2500 で検算）。
2. O(N²) の処理に上限を付ける以外の対策を、1つ挙げよ。
3. `Set.has` と `Array.includes` の違いを、計算量で説明せよ。
4. 乱数を使わず `cellDelay` にした利点を、2つ挙げよ。
5. `findTerms` が、短い用語を捨てる条件を、4つの条件で言え。

## 解答の方針

- 演習 11.1: 各周の `end = min(start+10, 25)`、次の `start = end - 3`。開始位置は 0, 7, 14（end=24）, 21（end=25 で break）→ 4個。長さは 10, 10, 10, 4。
- 演習 11.2: `start` が進まず、同じチャンクを永遠に追加（メモリが尽きる）。安全版は `if (overlap >= size) overlap = Math.floor(size / 2)` のように補正するか、`throw` する。
- 演習 11.3: `300×299 / (500×499) ≈ 0.36` 倍。約 6,900 万回。
- 確認問題 1: 最初の1個で `size` を使い、以降は1個ごとに `size - overlap` 進む。n=2500 → `(2500-150)/(1000-150) = 2.76…` の切り上げで 3。
- 確認問題 2: 近いものだけを比べる（空間分割・近似最近傍）、結果をキャッシュする、事前計算する。
- 確認問題 4: 再現できる（同じ入力で同じ絵）、テストで検証できる。

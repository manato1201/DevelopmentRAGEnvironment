# 第14回 グラフのアルゴリズム（配分・類似度・折り畳み・層配置）

**到達目標:** 「点と線」で表せる問題に対して、**このプロジェクトの4つのアルゴリズム**（比率配分・類似度のエッジ・鎖の折り畳み・層配置）を、**数を入れて追える**。入力の“規模”が増えたときの限界を言える。
**前提:** 第11回（計算量・Map/Set）、第12回（コサイン類似度）。 **目安:** 4時間

## 1. 全体像：グラフは2か所で使われている

| 場所 | 点（ノード） | 線（エッジ） | 目的 | ファイル |
|---|---|---|---|---|
| **Web 画面のグラフ** | 文書（チャンク） | 意味が近い文書どうし | 知識の地図を見せる | `src/graph.ts` |
| **Houdini のチュートリアル図** | Houdini のノード | 接続（入力→出力） | 100〜200ノードの図を読めるサイズにする | `tutorial_graph_simplify.py` `graph_diagram.py` |

## 2. 基礎

### 2.1 用語

| 用語 | 意味 |
|---|---|
| ノード（点）／エッジ（線） | 要素／要素どうしの関係 |
| **有向**／**無向** | 向きがある（A→B）／ない（A—B） |
| 次数（degree） | 1つのノードにつながる線の数。有向なら**入次数**（入ってくる）と**出次数**（出ていく） |
| **DAG** | 向きがあり、**ぐるぐる回る輪（サイクル）が無い**グラフ。Houdini のノードネットワークは DAG |
| 層（レイヤー） | 左から右へ、入力→出力の向きに並べた列 |

### 2.2 比率配分：最大剰余法（`allocateQuotas`）

**問題:** 画面に出せるノードは最大 500。しかし文書は 5,000 件ある。**どの namespace から、何件ずつ**出すか。先頭から切ると、偏る。**文書数の比率に合わせ、文書のある namespace は最低 1 件は出す。**

**アルゴリズム（`graph.ts`）:**

1. 合計が `maxNodes` 以下なら、**全件**（配分の必要なし）。
2. 文書のある namespace の数が `maxNodes` 以上なら、**文書数の多い順に 1 件ずつ**。
3. それ以外は、
   1. 各 namespace に **最低 1 件**を先に確保。
   2. 残りの枠 `spare = maxNodes − namespace数` を、「**各自の余り文書数（total − 1）**」の比率で割り振る。
   3. 小数の**整数部分**を先に配る。
   4. 配りきれなかった端数を、**小数部分の大きい順**に 1 件ずつ配る（**最大剰余法**）。

**数を入れた例（実測と一致を確認済み）:** 上限 500。A=600 件、B=300 件、C=99 件、D=1 件（合計 1,000）。

| 段 | A | B | C | D | 合計 |
|---|---|---|---|---|---|
| 最低1件 | 1 | 1 | 1 | 1 | 4 |
| 余り文書数（total−1） | 599 | 299 | 98 | 0 | 996 |
| 残り枠 `spare` = 500 − 4 | | | | | **496** |
| 理想の取り分 `spare × 余り / 996` | 298.30 | 148.90 | 48.80 | 0 | |
| 整数部分 | 298 | 148 | 48 | 0 | 494 |
| 端数の小数部分 | 0.30 | **0.90** | **0.80** | 0 | |
| 残り 2 枠 → 小数の大きい B・C に +1 | | +1 | +1 | | |
| **最終（1 + 整数部 + 端数）** | **299** | **150** | **50** | **1** | **500** |

> 実測の出力: `[A, 299] [B, 150] [C, 50] [D, 1]`。**小さな namespace（D）も 0 にならない**のが肝。

**なぜ単純に四捨五入しないのか:** 四捨五入だと、合計が 500 からずれる（499 や 501）。最大剰余法は、**必ず合計がちょうど**になる（**Hamilton 法**とも呼ばれる、議席配分の古典的な方法）。

**取り出し方:** 各 namespace から `ORDER BY chunk_id LIMIT quota`。`chunk_id` はハッシュ由来で偏りが無く、**呼び出しごとに同じ結果**になる（再現性）。

### 2.3 類似度のエッジ：全ペア比較（`handleGraph`）

```
① 各ノードの先頭チャンクのベクトルを Vectorize から取得（20件ずつ、4本並列）
② 長さ1に正規化（normalized）
③ 全ペア (i, j) の内積（＝コサイン類似度）を計算
④ 閾値 0.72 以上のものから、類似度の高い順に最大 5 本をエッジにする
⑤ 向きのないペアの重複を、Set で除く（2.4 の“小さいほうを先”のキー）
```

**小さな例（2次元）:** a=(1,0)、b=(0.8,0.6)、c=(0,1)（どれも長さ1）。

| ペア | 内積 | 0.72 以上？ |
|---|---|---|
| a–b | 0.8 | **はい → エッジ** |
| b–c | 0.6 | いいえ |
| a–c | 0 | いいえ |

**規模の限界（第11回の再確認）:** 全ペア＝ N(N−1) 回の内積。N = 500、次元 768 で約 1.9 億回の掛け算。`MAX_GRAPH_NODES = 500` はこの限界から決めた上限（1,000 では遅くなった、とコメント）。

**取得の小技:** `Vectorize.getByIds` は 1 回に最大 20 件。`chunkArray(ids, 20)` で分け、`GET_BY_IDS_PARALLEL = 4` 本ずつ `Promise.all`。**全部を同時に投げない**のは、サブリクエスト数や負荷を抑えるため。

**エッジの“上位5本”の意味:** 各ノードから見て上位 5 本。A から B が上位でも、B から A が上位でなければ、片方向だけ残る。無向グラフとして扱うので、**重複さえ除けば** 1 本の線になる。

### 2.4 鎖の折り畳み（`simplify_graph`）

**問題:** 生成されたチュートリアルのノードグラフは 100〜200ノード。一本道（A→B→C→D）が多く、**そのまま描くと塊になる**。

**考え方:** 「**分岐も合流もしない一本道**」は 1 つの箱にまとめても、情報は失われない。

**アルゴリズム:**

1. 各ノードの**入次数**・**出次数**を数える。
2. **線形ノード**＝入次数 ≤ 1 かつ 出次数 ≤ 1、かつ **コンテナ（サブネット等）でない**もの。
3. **線形ノードどうし**をつなぐ辺だけを、鎖として連結する（`chain_next[u] = v`、`chain_prev[v] = u`）。**親が違う**（別のサブネットをまたぐ）辺は、つながない。
4. 鎖の**先頭**（`chain_prev` を持たない線形ノード）から `chain_next` をたどって一本道を確定。**循環防止**（`seen_in_run`）。
5. 2 ノード以上の鎖を、1 つの集約ノード `chain::A->B->C` にする。1 ノードだけの鎖は、そのまま。
6. 辺は、**両端を代表ノードに置き換え**、鎖の内側の辺（`ru == rv`）は捨て、重複を除く。

**数を入れた例（実測）:**

```
grid1 → mountain1 → scatter1 → split1 ─┬→ a1 → a2 ──→ merge1 → out1
                                        └→ b1 ──────↗
```

| ノード | 入次数 | 出次数 | 線形？ | 理由 |
|---|---|---|---|---|
| grid1 | 0 | 1 | ○ | |
| mountain1 | 1 | 1 | ○ | |
| scatter1 | 1 | 1 | ○ | |
| **split1** | 1 | **2** | ✕ | 分岐 |
| a1 | 1 | 1 | ○ | |
| a2 | 1 | 1 | ○ | |
| b1 | 1 | 1 | ○ | 鎖の長さ 1（折り畳み相手がいない） |
| **merge1** | **2** | 1 | ✕ | 合流 |
| out1 | 1 | 0 | ○ | 前が merge1（線形でない）ので、鎖は長さ 1 |

結果（9ノード → **6ノード**）:

| 新しいノード | 中身 |
|---|---|
| `chain::grid1->mountain1->scatter1` | 3ノードの鎖 |
| `chain::a1->a2` | 2ノードの鎖 |
| `split1` / `b1` / `merge1` / `out1` | そのまま |

辺: 鎖1→split1、split1→鎖(a1,a2)、split1→b1、鎖(a1,a2)→merge1、b1→merge1、merge1→out1（6本）。**分岐・合流点は“境目”として必ず残る**（隣が線形ノードでも、そこで鎖は切れる）。

**Mermaid への変換（`graph_to_mermaid`）:** 上の結果は、次のテキストになる。

```
flowchart TD
    chain__grid1__mountain1__scatter1["grid1 → mountain1 → scatter1（3ノード）"]
    chain__a1__a2["a1 → a2（2ノード）"]
    split1("split1")
    ...
    chain__grid1__mountain1__scatter1 --> split1
```

ID は英数字とアンダースコアだけに直す（`_mermaid_id`）。**記号が入ると Mermaid が構文エラーになる**ため。ラベルの `"` と改行も無害化（`_mermaid_label`）。

### 2.5 層配置：トポロジカルソートと重心法（`layered_positions`）

**問題:** Houdini のネットワークエディタの座標は、**密集・重なり**が多く、そのまま描くと読めない。**接続の構造だけ**から、左→右の層に並べ直す。

**ステップ1：トポロジカルソート（Kahn 法）— `_topo_order`**

「**親（入力側）が全部済んでから、子を出す**」順に並べる。

1. 各ノードの入次数を数える。
2. 入次数 0 のノードを**キュー**に入れる。
3. キューから取り出し、結果に追加。**その子の入次数を 1 減らし**、0 になったらキューに入れる。
4. 繰り返す。

小例: a→c、b→c、c→d。入次数 a0・b0・c2・d1。キュー [a, b] → a を出す（c が 1）→ b を出す（c が 0 → キューへ）→ c を出す（d が 0）→ d。順序は **a, b, c, d**。

**サイクルが混入しても止まらない:** 取りこぼしたノードは**末尾にそのまま足す**（例外を出さず、常に何かの順序を返す安全策）。

**ステップ2：層番号 = 親からの最長経路**

`depth[ノード] = max(親の depth) + 1`（親が無ければ 0）。**最長**にするのは、全部の入力より右に置くため（短いほうに合わせると、線が逆向きになる）。

**ステップ3：層の中の並び順 = 重心（barycenter）**

同じ層のノードを、**親の縦位置の平均**でソートする。親が上にあるノードは上に、下にあるノードは下に来る＝**線の交差が減る**。層 0 だけは、名前順。

**ステップ4：中央揃え**

層のノード数 n から `offset = (n−1)/2`、各ノードの縦位置を `i − offset`（i は 0 始まりの順番）。上下に偏らず、左右対称の見た目になる。

**数を入れた例（実測。2.4 の結果に適用）:**

| ノード | 層（`col`） | 縦位置（`row`） |
|---|---|---|
| `chain::grid1->…->scatter1` | 0 | 0.0 |
| `split1` | 1 | 0.0 |
| `chain::a1->a2` | 2 | **−0.5** |
| `b1` | 2 | **+0.5** |
| `merge1` | 3 | 0.0 |
| `out1` | 4 | 0.0 |

層 2 の2ノード（n=2）は `offset = 0.5` なので、−0.5 と +0.5。親（split1）の縦位置はどちらも 0 で**同点**→ 元の並び順を保つ（安定ソート）。**戻り値は格子座標**で、呼び出し側（`tutorial_view.py`）が**スケールをかけて**画面の座標にする。

> これは **Sugiyama 法**（階層グラフ描画の古典）の簡易版です。完全版には、サイクルの除去・ダミーノードの挿入・交差最小化の反復が加わります。**今の実装は、DAG・数百ノードまで**を想定した軽量版、と覚えておいてください。

### 2.6 「ひとつのネットワーク」を選ぶ（`pick_container`）

動画の説明スライド用に、**1枚の図に出すネットワーク（親ノード）**を選びます。深いサブネット（APEX など）の内部の数十ノードを選ぶと、読めない図になるため、**浅い親**を選びます。

```python
return min(candidates, key=lambda p: (p.count("/"), -counts[p], p))
#                                    ↑ 浅い     ↑ 直下の数が多い  ↑ 同点は名前順
```

実測: `/obj/geo1`（直下 2）と `/obj/geo1/sub`（直下 2）なら、スラッシュの数が少ない **`/obj/geo1`** を選ぶ。**`min` の `key` をタプルにすると、優先順位つきの比較**が書ける（タプルは先頭から順に比べる）。

### 2.7 時間の予算つきの走査（`scan_error_nodes`）

Houdini のシーンは巨大なことがある。**画面を止めない**ため、走査に**件数と時間の上限**を付けます。

```python
if scanned > limit or (scanned % 64 == 0 and clock() > deadline):
    return found          # 打ち切り（それまでに見つけた分を返す）
```

- **時計を毎ノード見ない**（`scanned % 64 == 0` のときだけ）。時計の呼び出し自体が重いため。
- **時計を引数にする**（`clock=time.monotonic`）。テストでは**偽の時計**を渡して、打ち切りを再現できる（`test_pilot_task.py`）。
- **打ち切ったら“少なく数える”**——これは仕様で、評価の集計はこの前提で読む（`pilot_task.py` の冒頭に明記）。

## 5. つまずきやすい点

- **「四捨五入で配れば合う」と考える。** 合計がずれる。端数の処理（最大剰余法）が要る。
- **一本道は全部まとめてよい、と考える。** 分岐・合流点は残す。**コンテナ**（サブネット）と、**親の違い**も境目。
- **座標をそのまま使う。** 生の座標は密集・重なりが多い。構造から作り直す。
- **循環を想定しない。** 実データでは「起きないはず」が起きる。**安全策を入れて、止まらない**ようにする。
- **時計を毎回見る。** 走査が遅くなる。間引いて見る。

## 6. 確認問題

1. 最大剰余法が、四捨五入より優れている点は？
2. 線形ノードの条件を、3つで言え。
3. なぜ分岐点・合流点は、鎖の途中に含めないのか。
4. 層番号を「最長経路」で決める理由は？
5. `scanned % 64 == 0` を条件にする理由は？

## 解答の方針

- 演習 14.1: 最低1件ずつ（3件）、残り枠 97。余り文書数 69・39・1（合計 109）。理想 `97×69/109=61.40`、`97×39/109=34.71`、`97×1/109=0.89`。整数部 61・34・0（計 95）、端数 2 枠。小数部 .40・.71・.89 → C（.89）と B（.71）に +1。**A=62, B=36, C=2**（1+61, 1+34+1, 1+0+1）。合計 100。
- 演習 14.2: 線形ノード: a, b, c（入1・出1）、d（入1・出1）。s は出次数 2（非線形）、t は入次数 2（非線形）。鎖は `chain::a->b->c`（3ノード）。d は鎖の長さ 1 でそのまま。ノード: `chain::a->b->c`, `s`, `d`, `t`。辺: s→鎖、鎖→t、s→d、d→t。
- 演習 14.3: s=(0,0)、鎖=(1,−0.5)、d=(1,+0.5)、t=(2,0)（層 1 は 2 ノードで offset 0.5。親がどちらも s で同点→元の順）。順序は入力ノードの並びに依存する点に注意。
- 演習 14.5: `_topo_order` が、取りこぼしたノードを末尾に足す。`depth` の計算は、`order` に従って 1 周するだけなので、無限ループにならない。
- 確認問題 3: 分岐点・合流点を含めると、図の“意味のある境目”が消える（どこで分かれたか分からない）。

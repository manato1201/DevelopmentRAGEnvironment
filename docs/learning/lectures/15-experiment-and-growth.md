## 2. 基礎

### 2.1 割り当て：ラテン方格（順序効果を打ち消す）

**問題:** 3つの課題（Pyro・RBD・雲）を、全員が同じ順（1回目 Pyro …）で行うと、「**最初の回は慣れていない**」「**最後の回は疲れている**」という**順序の影響**が、課題や条件の差と混ざる。

**対策:** **ラテン方格**＝各行・各列に、各要素がちょうど1回ずつ出る表。参加者を3つの組（slot）に分け、課題の順序を回してずらす。

```ts
export const LATIN = {
  1: ["pyro", "rbd",  "cloud"],     // slot 1 … 1回目 pyro, 2回目 rbd,  3回目 cloud
  2: ["rbd",  "cloud","pyro"],
  3: ["cloud","pyro", "rbd"],
};
slotForPid(pid) = ((pid − 1) % 3) + 1       // pid 1,2,3,4,5,6,7 → slot 1,2,3,1,2,3,1
対照の回（docs_only） = 回 == slot
```

**一覧にすると（条件込み）:**

| slot | 1回目 | 2回目 | 3回目 |
|---|---|---|---|
| 1 | Pyro（**対照**） | RBD | 雲 |
| 2 | RBD | 雲（**対照**） | Pyro |
| 3 | 雲 | Pyro | RBD（**対照**） |

**読み取れること:**

- 縦に見ても（各回）、横に見ても（各 slot）、**3つの課題が1回ずつ**。順序が**偏らない**。
- **対照の課題**は、slot 1 = Pyro、slot 2 = 雲、slot 3 = RBD。**3つの課題が、それぞれ1度ずつ“対照”**に当たる。課題の難しさの違いが、条件の差に**一方的に**混ざらない。
- **回 == slot** が対照、というたった1行が、この設計の中心。

**割り当ての実測:** `slotForPid` は 1〜7 に対して `1, 2, 3, 1, 2, 3, 1`（実測）。

> **限界（正直に）:** 参加者数が **3の倍数でない**と、slot の人数が揃わず、バランスが崩れる。さらに、各人の比較は「**システムを使った2回の平均 − 対照の1回**」で、**異なる課題どうしの差**になる（課題の難しさの違いは、人数が揃ったときに全体で相殺されるだけ）。**少人数では、個々の数字の“差”を、課題の影響と切り分けられない**。

### 2.2 いまの回を決める（`buildPlan`）

「**第N回が完了**」＝その回の `fixed` と `free` の**両方**が `ended_at` を持つ。

```ts
let completed = 0;
while (completed < ROUNDS && done(completed + 1, "fixed") && done(completed + 1, "free")) completed++;
const round = Math.min(completed + 1, ROUNDS);          // いまの回（最大3）
const taskId = LATIN[slot][round − 1];
condition = (round === slot) ? "docs_only" : "system";   // 固定課題のみ。自由課題は常に system
```

**トレース（実測）:** slot 2 の参加者。1回目の固定・自由が完了、2回目の固定が開始済み（未完了）。

| 項目 | 値 | 理由 |
|---|---|---|
| `completedRounds` | 1 | 1回目だけ両方済み |
| `round` | 2 | 1 + 1 |
| `taskId` | `cloud` | `LATIN[2][1]` |
| `condition` | `docs_only` | `round(2) === slot(2)` |
| `fixed.active` | true | 開始したが `ended_at` が無い |

**ここがやり直し（第8回）の設計の肝:** 履歴は“計算で求める”（`sessions` から毎回導く）ので、**行を破棄（`discarded_at`）すれば、計画が自動的に巻き戻る**。「いまの回」を別に保存していないから、ずれようがない。

### 2.3 時間の計測：引き算の落とし穴を潰す

サーバー側（`handlePilotSessionEnd`）の式：

```
endedAt   = max(started_at, now − surveySec)                  … 「終了」を押した時刻（回答に使った時間を引く）
pausedSec = min(clamp(pausedSec, 0, 604800), endedAt − started_at)   … 中断は、経過時間を超えない
duration  = endedAt − started_at − pausedSec
queries   = COUNT(memory) where created_at ∈ [started_at, endedAt]
```

**数を入れた例:** 開始 `started_at = 1000`、送信時刻 `now = 4000`、アンケートの回答に 240 秒、Houdini を閉じていた中断 600 秒。

| 項目 | 計算 | 値 |
|---|---|---|
| `endedAt` | `max(1000, 4000 − 240)` | 3760 |
| `pausedSec` | `min(600, 3760 − 1000 = 2760)` | 600 |
| `duration` | `3760 − 1000 − 600` | **2160 秒（36分）** |

**なぜ clamp するか:** クライアントから来る値は**信用しない**（バグや改ざん）。`pausedSec` が 5000 と申告されても、`min(…, 2760)` で 2760 になり、`duration` は **0 を下回らない**。`surveySec` が巨大でも `max(started_at, …)` で、`endedAt` が開始より前にならない。`clampInt` は NaN・文字列も既定値に直す（`http.ts`）。

> **原則:** 時間の式は、**必ず境界の値（0・巨大・負・NaN）で確かめる**。

### 2.4 Houdini 側の計測：集合と中断

**cook エラー数 = “一度でもエラーになったノードの数”**（のべ回数ではない）。

```python
self._paths |= scan_error_nodes(self._hou)      # 集合の和（同じノードは何度出ても1つ）
count = len(self._paths) if self._hou is not None and self.samples > 0 else None
```

- **集合**にするので、同じノードが何度エラーでも 1。**サンプリングの間隔（20秒）**に直ったエラーは数えられない＝**実際より少なく出うる**（仕様。冒頭の docstring に明記）。
- **測れない**ときは `None`（空欄）。**0 とは区別する**（0 = 測って、無かった）。

**再開（`resume_state`）:**

```python
gap    = max(0, now − lastSeen)
paused = savedPausedSec + (gap if gap >= PAUSE_MIN_SEC(40) else 0)
```

実測：

| 入力 | 結果 |
|---|---|
| 保存 `{errorPaths:[/obj/a], pausedSec:30, lastSeen:1000}`、再開 `now = 1100`（空き100秒） | 引き継ぐノード `{/obj/a}`、中断 **130**（30 + 100） |
| 保存 `{pausedSec:30, lastSeen:1000}`、再開 `now = 1030`（空き30秒） | ノード `{}`、中断 **30**（空きが40秒未満は数えない） |
| 保存なし | `({}, 0)` |

**40秒の理由:** 保存の間隔が20秒。**間隔の倍**（40秒）以上空いたら「閉じていた」とみなす。**重くて固まっていただけ**の時間は、作業の時間なので引かない。

### 2.5 操作ミスのスコア（`mistakeScore`）

```
cook = min(max(cookErrorNodes, 0), 10) / 10                 … 0〜1（10個以上は 1）
self = (min(max(selfMistakes, 1), 5) − 1) / 4               … 1〜5 を 0〜1 に
score = 0.7 × cook + 0.3 × self                              … 小数第3位で丸め
```

| 入力 | 計算 | 結果（実測） |
|---|---|---|
| cook 4、self 3 | `0.7×0.4 + 0.3×0.5 = 0.28 + 0.15` | **0.43** |
| cook 0、self 1 | `0 + 0` | **0** |
| cook 15、self 5 | `0.7×1 + 0.3×1`（cook は上限 10 で 1） | **1** |
| cook なし（None） | — | **null**（片方だけで代用しない） |

**設計の意図:** メカニクス面（cook エラー）7割 + ビジュアル操作面（自己申告）3割。**どちらも 0〜1 にそろえてから**合わせる（単位が違うものは、そのまま足さない）。**上限 10** は“これ以上は同じ（最大）とみなす”打ち切り。**片方が無ければ null**：もう片方で“代用”すると、別の物差しの数字が混ざる。

**変える前に:** 重み 0.7/0.3 と上限 10 は、`MISTAKE_WEIGHT_*`・`COOK_ERROR_CAP`。**実験の途中で変えると、前後のデータが比べられなくなる**。変えるなら、**日付と理由を記録**し、旧式の値も併記する。

### 2.6 集計：中央値と“対応のある差”

**中央値（`median`）:** 外れ値に強い代表値。小さい順に並べ、真ん中（偶数個なら中央2つの平均）。実測：`[3,1,2]` → 2、`[4,1,3,2]` → 2.5、`[null,5]` → 5（null は除く）。

**対応のある差（`summarizeTasks` の `paired`）:** 同じ参加者の中で、

```
diff = （システムを使った回の平均） − （対照の回）        … 参加者ごとに1つ
```

指標ごとに、`diff` を集めて、**中央値の差**・**改善した人数**（`lower` なら `diff < 0`、`higher` なら `diff > 0`）・**rank-biserial 相関**を出す。

### 2.7 rank-biserial 相関：差の“そろい具合”

`diff` の**符号**（どちら向きか）と**大きさの順位**を使う、**-1〜1** の指標です（Wilcoxon の符号付き順位から）。

1. 0 の差は除く。
2. **絶対値**の小さい順に順位をつける。**同じ絶対値は平均順位**。
3. 正の差の順位の合計 `plus`、負の差の順位の合計 `minus`。
4. `r = (plus − minus) / (plus + minus)`。

**手計算（実測と一致）①:** `diffs = [-2, -1, 3, -1, 0]`

| 手順 | 値 |
|---|---|
| 0 を除く | `-2, -1, 3, -1` |
| 絶対値の小さい順 | `1(-1), 1(-1), 2(-2), 3(+3)` |
| 順位（同じ絶対値 1 は平均 `(1+2)/2 = 1.5`） | `1.5, 1.5, 3, 4` |
| `plus`（正の差 +3 の順位） | 4 |
| `minus` | `1.5 + 1.5 + 3 = 6` |
| `r` | `(4 − 6) / 10 = −0.2` |

**手計算 ②:** `diffs = [-3, -2, -1, 1]`（所要時間（分）で、3人が短く、1人が長い）→ 順位 `1.5(−1), 1.5(+1), 3(−2), 4(−3)` → `plus = 1.5`、`minus = 1.5 + 3 + 4 = 8.5` → `r = (1.5 − 8.5)/10 = −0.7`。`improved`（lower の指標で `diff < 0`）= 3、`medianDiff = (−2 + −1)/2 = −1.5`。

**読み方:** `lower` が良い指標（所要時間・ミス）で **負に大きい**ほど、「システムを使った回のほうが、**そろって**良い」。**±1 に近い**＝そろっている、**0 付近**＝そろっていない。

> **限界（必ず添える）:** n=4 の `-0.7` は、**偶然でも出る**。この値は“**そろい具合の記述**”で、**有意性の判定ではない**。参加者が増えたら、分析設計書（`docs/pilot-analysis-design.md`）に沿って、別途、検定や信頼区間を使う。

### 2.8 習熟度（成長）：点の合計としきい値

`growth.ts` の式：

```
各用語の点 = 段階の点（basic 1 / applied 2 / advanced 3） × min(回数, 3) / 3      … 同じ用語は3回までを数える
スコア = 全用語の点の合計（小数第1位で丸め）
レベル = スコア ≥ 18 なら advanced、≥ 6 なら applied、それ以外 basic
```

**数を入れた例（実測）:** 用語 `SOP`（basic）5回、`アトリビュート`（applied）2回、`VEX`（applied）1回、`PDG`（advanced）3回。

| 用語 | 段階の点 | min(回数,3)/3 | 点 |
|---|---|---|---|
| SOP | 1 | 3/3 = 1 | 1.0 |
| アトリビュート | 2 | 2/3 | 1.33 |
| VEX | 2 | 1/3 | 0.67 |
| PDG | 3 | 3/3 = 1 | 3.0 |
| **合計** | | | **6.0** → **applied**（しきい値 6 ちょうど） |

**設計の意図:**

- **3回で頭打ち**：1つの用語を連呼しても、スコアが膨らまない。
- **段階の高い用語ほど点が大きい**：難しい用語を使えるほど上がる。
- **質問の全文は保存せず**、**用語と回数だけ**を蓄積（プライバシー）。

**一段やさしくする（`lowered`）:** 直近3件の評価が**すべて -1（役に立たなかった）**で、かつスコアのレベルが basic でないとき、**一段下げる**。同じ例で `[-1,-1,-1]` を渡すと、`scoreLevel = applied` のまま `level = basic`、`lowered = true`（実測）。**使いこなしている用語**（回数 ≥ 2）は、`SOP`・`アトリビュート`・`PDG`（`VEX` は1回なので入らない）。

**変える前に:** しきい値 6・18、`KNOWN_COUNT = 2`、`min(回数, 3)` は、**利用者の体験**に直結する。実証実験の途中で変えると、「レベルが急に変わった」と見えてしまう。**変えるなら告知し、分析にも記録**する。

### 2.9 公開の制限：k-匿名（最小人数）

`pilotStats.ts` は、管理画面に出す集計を、**個人が特定できない形**にします。

- **習熟度の分布**は、参加者が `MIN_GROUP = 3` 人**未満**なら、**出さない**（理由の文だけ返す）。2人だと、「片方が advanced なら、もう片方も推測できる」ため。
- **よく使われた用語**は、**2人以上**が使ったものだけ（`MIN_USERS_PER_TERM = 2`）。1人だけが使った珍しい用語は、その人を特定しうる。
- **管理者アカウント自身の利用は数えない**（`role != 'admin'`）。運営のテストが混ざらない。
- **日数は 1〜365 に clamp**（`clampDays`）。

> これは **k-匿名性**（同じ特徴を持つ人が k 人以上いるときだけ公開する）の、簡単な形。**最小人数を変える**ときは、告知文（`pilot-announcement.md`）の約束と**必ず合わせる**。

## 3. このプロジェクトでは：式を変えたいときの手順

1. **どの式か**を特定する（上の表）。
2. **現在の挙動を、数値例でテストに固定**する（`test/pilot_tasks.test.mjs`、`test/growth.test.mjs`）。
3. 式を変え、**境界値**（0・上限・null・負）でもテストを足す。
4. **実験の途中なら、旧式の値を残す**（列を足す、または記録に残す）。比較できなくなる変更は、**運営に相談**。
5. 告知・分析設計書に影響があれば、**その場で直す**。
6. 本番へは第9回の手順で。

## 5. つまずきやすい点

- **「差が大きい＝効果がある」と読む。** 少人数では偶然で出る。**記述として扱う**。
- **式を、実験の途中で直す。** 前後のデータが比べられなくなる。
- **null と 0 を混ぜる。** 「測れなかった」と「無かった」は別。
- **クライアントの値を信じる。** サーバー側で **clamp** する。
- **サンプリングを“全数”と思う。** cook エラーは、20秒ごとの採取＝**少なく出うる**。

## 6. 確認問題

1. ラテン方格で、順序効果が打ち消される理由を説明せよ。
2. `round === slot` が対照になる設計で、各課題が対照に1度ずつ当たる理由は？
3. `pausedSec` を `endedAt − started_at` で `min` する理由は？
4. `mistakeScore` が、片方が null のとき null を返す理由は？
5. rank-biserial が `-1` のとき、何を意味するか。
6. `MIN_USERS_PER_TERM = 2` の意味は？

## 解答の方針

- 演習 15.1: slot 3 → 1回目 雲（system）、2回目 Pyro（system）、3回目 RBD（**docs_only**）。pid 8 → `((8−1)%3)+1 = 2`。
- 演習 15.2: `endedAt = max(5000, 9000−300) = 8700`、`pausedSec = min(1000, 3700) = 1000`、`duration = 8700−5000−1000 = 2700`（45分）。`pausedSec = 9000` なら `min(9000, 3700) = 3700`、`duration = 0`。
- 演習 15.3: `cook = 0.7`、`self = (2−1)/4 = 0.25`。`0.7×0.7 + 0.3×0.25 = 0.49 + 0.075 = 0.565`。
- 演習 15.4: `median([-1,-1,2,4,-3,0]) = (−1 + 0)/2 = −0.5`（昇順 `−3,−1,−1,0,2,4`、中央2つが −1 と 0）。`improved` = 負の数 = 3。`rank-biserial`: 0 を除き `−1,−1,2,4,−3`、絶対値順 `1,1,2,3,4` → 順位 `1.5,1.5,3,4,5`（`−1,−1,+2,−3,+4`）、`plus = 3 + 5 = 8`、`minus = 1.5+1.5+4 = 7`、`r = 1/15 = 0.067`。
- 演習 15.5: `Pyro` = 2×min(4,3)/3 = 2、`ノード` = 1×1/3 = 0.33、`USD` = 3×2/3 = 2。合計 4.33 を小数第1位で丸めて **4.3** → **basic**（< 6）。（実測: `4.3 basic`）
- 演習 15.7: 3つの slot の人数が揃わない（例: 4/3/3）。対照の課題が、ある課題に偏る。**補い方:** 参加者の登録順（pid）を 3 の倍数で締める、結果に slot の人数を併記する、少人数のうちは差を“記述”にとどめる。
- 演習 15.8: 2人だと、自分の情報と全体の分布から、**もう1人の習熟度が推測できる**（k=2 では、片方が分かれば他方が分かる）。告知文の「個人が特定されない形」の約束にも反する。

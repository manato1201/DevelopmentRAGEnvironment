到達目標: 「止める・数える・待つ」ためのコードを、競合（同時に来たとき）と失敗（途中で落ちたとき）の目で読める。予約→実行→清算の予算方式を、数を入れて説明できる。
前提: 第3回（SQL）、第5回、第11・12回。 目安: 4時間

1. 全体像：1回の質問が通る「関門」

src/query.ts の準備段階（prepareQuery）は、この順に関門を通ります。順序には理由があります。

① authenticate        … APIキー → userId（ハッシュ）→ 権限（auth.ts）          [index.ts]
② resolveEffective…   … 許可された namespace だけに絞る
③ assertNotRateLimited … 直近60秒に30回以上なら 429（rateLimit.ts）
④ startAuditLog       … 監査ログの「仮の行」を先に書く（auditLog.ts）          ← 高価な処理の前
⑤ reserveBudget       … トークン予算を「予約」。足りなければ 429（budget.ts）
⑥ retrieve → 生成      … HyDE・埋め込み・検索・回答（高価。お金がかかる）
⑦ reconcileBudget     … 実測との差分を清算（失敗したら全額払い戻し）
⑧ finalizeAuditLog    … 仮の行を、結果で埋める

設計の原則: ①〜⑤は安い処理で、⑥が高い処理。安い関門を先に置き、高い処理の前に“予約”を済ませる。⑥で失敗したら⑦で払い戻す。

2. 基礎

2.1 認証：キーは保存せず、ハッシュだけを比べる

const userId = await sha256Hex(apiKey);          // SHA-256 → 16進64文字
return loadAuthedUser(env, userId);               // users テーブルから引く
  • ハッシュは、元に戻せない一方向の変換。D1 に残るのは userId（＝キーのハッシュ）だけなので、D1 が漏れても、キーそのものは漏れない。
  • 管理画面に出る「ID の先頭6文字」（userIdShort）は、キーではなくハッシュの先頭。
  • 期限切れは、「存在しない」と同じ応答にする（loadAuthedUser）。別の文言にすると、「そのキーは実在する」と攻撃者に教えてしまうため。
  • 権限の決め方: admin は全 shared + 自分の personal。それ以外は、key_namespace_grants で許可された shared + 自分の personal。SQL の OR の括り方（(A AND B) OR C）が、この仕様そのもの。

2.2 回数制限：直近 60 秒を数える

const since = now - 60;
SELECT COUNT(*) FROM audit_log WHERE user_id = ? AND created_at >= ?;   // 30 以上なら拒否

専用の表を増やさず、すでにある audit_log を数えるのが工夫です。

方式の名前に注意: ソースのコメントは「固定ウィンドウ」と書いていますが、動きとしてはスライディングウィンドウ（ログ方式）です。

方式 数え方 弱点
固定ウィンドウ 時刻を 0:00〜0:59、1:00〜1:59 … と区切り、区間ごとに数える 区切りをまたぐと、2秒間に上限の2倍が通る（0:59 に 30 回 + 1:00 に 30 回）
スライディング（今の実装） 「今」から 60 秒さかのぼって数える 区切りが無いので、上の問題は起きない。代わりに、毎回 COUNT を打つ（created_at に索引があるので範囲は絞れる）
トークンバケット 一定の速さで“券”が貯まり、1回ごとに1枚使う 実装が少し複雑。バーストを許したいときに向く

学び: コメントの用語は鵜呑みにせず、コードの動きで確かめる。ここでは、どちらの用語でも、制限の強さ（60秒に30回）は変わりません。

ただし、数えるのは“書き込み済みの行”だけです。書き込み前の同時リクエストは見えません——次の2.3が、その対策です。

2.3 同時リクエスト：確認してから書くは破れる（TOCTOU）

TOCTOU（Time Of Check To Time Of Use）＝「確認した時点」と「使う時点」の間に状況が変わる問題。

リクエストA: COUNT = 29 → OK → （高価な処理…）→ 最後に audit_log へ書く
リクエストB: COUNT = 29 → OK → （高価な処理…）→ 最後に audit_log へ書く
           ↑ AもBも「まだ誰も書いていない」ので両方通る。30件の同時リクエストが全部通る

対策（2026-09-04）: 高価な処理の前に、startAuditLog で仮の行を書く。この行自体が「いま実行中」という予約になり、後続の COUNT(*) に見える。処理後に、finalizeAuditLog で結果（件数・遅延・トークン）だけを埋め戻す。

正直な限界: ③の確認と④の書き込みの間には、わずかな窓が残ります（厳密な排他ではない）。上限を守る「目安」としては十分、というのが、このプロジェクトの判断です。厳密にしたいなら、確認と書き込みを1つの SQL にする（次の2.4と同じ考え方）。

2.4 予算：予約 → 実行 → 清算（原子的な更新）

LLM の呼び出しは、終わるまで、何トークン使うか分からない。そこで、

  1. 見積もりを先に“予約”する（reserveBudget）。上限を超えるなら、その場で拒否（429）。
  2. 実行する。
  3. 実測との差分だけ、清算する（reconcileBudget）。少なければ払い戻し、多ければ追加。失敗したら全額払い戻し。

核心は、予約の SQL が1文であること。

UPDATE token_budgets
   SET used_tokens = used_tokens + :estimate
 WHERE user_id = :u AND budget_type = :t
   AND used_tokens + :estimate <= limit_tokens;     -- 条件に合う行だけ更新される
-- 更新された行数 (meta.changes) が 0 なら、予算不足

なぜ1文か（競合の例・実測）: 上限 10,000、使用済み 9,000（残り 1,000）に、800 の予約が2件ほぼ同時に来る。

方式 流れ 結果
確認してから書く（2回の往復） A: 残り1,000 ≥ 800 → OK。B: 残り1,000 ≥ 800 → OK。A書く（9,800）、B書く（10,600） 上限超え
条件つき UPDATE（1文） A: 9,000+800 ≤ 10,000 → 更新（9,800）。B: 9,800+800 = 10,600 > 10,000 → 0行（拒否） 守られる

実測（偽の D1 で reserveBudget を2回続けて呼ぶ）: 結果は true, false、used_tokens = 9800。D1 / SQLite は書き込みを直列に処理するので、UPDATE … WHERE の条件は「その時点の最新の値」で評価されます。

数を入れた通し（実測）: 上限 10,000・使用済み 5,000、見積もり 4,000。

手順 内容 used_tokens
予約 5,000 + 4,000 = 9,000 ≤ 10,000 → 成功 9,000
実行 実際に使ったのは 1,800 —
清算 delta = 1,800 - 4,000 = -2,200 → 払い戻し 6,800
次の予約 6,800 + 4,000 = 10,800 > 10,000 → 拒否 6,800

清算の SQL は MAX(0, used_tokens + delta)。マイナスにならないようにしています。

予算の無いユーザーは無制限: 行が無ければ reserveBudget は true（開発・検証用の既定）。本番で上限を付けたいキーには、必ず行を作る（管理画面の予算）。

2.5 ★読み取り練習：予定リセットの「遅れ」（修正済み）

applyScheduledResetIfDue（budget.ts）は、アクセスのたびに「リセット時刻を過ぎていれば使用量を 0 に戻す」遅延評価です（Cron が要らない）。以前の実装には癖があり、のちに修正しました（下の「修正後」）。以下は、修正前の挙動の記録です。

const nextResetAt = row.reset_at + row.reset_interval_hours * 3600;   // 【修正前】1周期ぶんしか進めない

実測（偽の D1）: 24時間周期のリセットが 72時間遅れ（3周期分、誰も使わなかった）で、使用済み 9,500、上限 10,000。そこへ 3,000 の予約を 4 回続ける。

回 予約の前の使用量 予約の後の使用量 reset_at
1 9,500 3,000（リセットされて 0 → +3,000） まだ過去
2 3,000 3,000（また、リセット） まだ過去
3 3,000 3,000（また、リセット） まだ過去
4 3,000 3,000 未来になった（ここで追いつく）

読み取れること: 長く使われなかったあとの最初の数回（遅れた周期の数だけ）は、予約が積み上がらず、上限が実質効かない。影響は限定的（最大で、遅れた周期の数 × 1回ぶん）ですが、仕様として意図したものではなさそうです。

修正後（2026-10-30。本番へは未デプロイ）: 「次のリセット時刻＝現在より後で最初の境界」にした。元のリズム（reset_at ＋ 周期の整数倍）は保たれる。

const periods = Math.floor((now - row.reset_at) / interval) + 1;   // interval は秒
const nextResetAt = row.reset_at + periods * interval;

進め方の見本: ①テストを先に書き（test/budget.test.mjs。上の4行の表を、そのままテストにして、修正前のコードで失敗することを確かめた）→ ②直す → ③第9回の手順で出す。本番のデータ（reset_at）は、変えない（コードを直せば、次のアクセスで自然に追いつく）。本番に出すのは、第9回の手順どおり、人が操作の名前を挙げて許可してからです。

2.6 タイムアウト：Promise.race と AbortController

外部 API は、遅いことがある。待つ時間に上限が要ります（chunking.ts の withAbortTimeout）。

const controller = new AbortController();
const timeout = new Promise<never>((_, reject) => {
  timer = setTimeout(() => { controller.abort(); reject(new Error("…タイムアウト")); }, ms);
});
try { return await Promise.race([fn(controller.signal), timeout]); }
finally { clearTimeout(timer!); }
部品 役割
Promise.race([A, B]) 先に終わったほうの結果で進む（もう片方は止まらない）
AbortController.abort() fetch などに渡した signal を通じて、止められるものを止める
clearTimeout 先に終わったとき、タイマーを残さない（finally）

歴史（コメントに記録）: 最初は Promise.race だけだった。しかし、負けた側の fetch は裏で動き続け、Worker 全体の実行時間を使い切って 503 になった（2026-08-27）。そこで、abort() で止められるものは止め、race で確実に次へ進むの二段にした。

学び: 「待つのをやめる」と「止める」は別物。両方が要る。

2.7 ストリーム（SSE）：切れ目で区切る

回答を届いた分ずつ画面に出す（generateContentStream）。サーバーからは、data: {...} の行が、空行（\n\n）で区切られた“イベント”として流れてきます。ただし、ネットワークの1回の受信が、イベントの途中で切れることがあります。

buffer += decoder.decode(value, { stream: true });     // 途中で切れた多バイト文字を壊さない
buffer = buffer.replace(/\r\n/g, "\n");                // 改行コードをそろえる
while ((idx = buffer.indexOf("\n\n")) !== -1) {        // 完結したイベントだけ取り出す
  handleEvent(buffer.slice(0, idx));
  buffer = buffer.slice(idx + 2);                       // 残り（不完全な部分）は次回へ持ち越す
}

トレース（1つのイベントが、2回に分かれて届く）:

受信 buffer（処理前） 処理 buffer（処理後）
1回目 data: {"a": data: {"a": \n\n が無い → 何もしない data: {"a":
2回目 1}\n\ndata: {"b":2}\n\n data: {"a":1}\n\ndata: {"b":2}\n\n 2つ取り出す ""
  • 壊れたイベントは読み飛ばす（try { JSON.parse } catch { return }）。1個の不具合で、回答全体を失わない。
  • 思考（thought）のパートは、本文に含めない。
  • 最後に、buffer に残りがあれば処理する（終端の空行が無い場合）。

2.8 D1 への書き込み：バッチと「分けてはいけない組」

runStatementGroups（chunkRows.ts）は、SQL を 50 文ずつまとめて DB.batch（1往復・1トランザクション）で実行します。

  • 組（グループ）は分けない。 putChunkStatements の4文（古い行を消す→FTS に挿入→chunk_rows に記録）は、隣り合う順序に意味がある（直前の last_insert_rowid() を使う）。
  • だから: 現在のバッチに入りきらないなら、グループごと次のバッチへ（if (current.length + g.length > maxPerBatch) await flush()）。

間接表（chunk_rows）の理由: chunks_fts の chunk_id・namespace・file は UNINDEXED 列で、これらで探す・消すと毎回全件走査になる（D1 の読み取り行数を使い切る原因だった。事例 A）。そこで、chunk_id → FTS の rowid の対応表を持ち、削除・参照は rowid 経由にした。書き込みは必ずこのファイルの関数を通す（片方だけ更新すると対応がずれる）。

2.9 冪等な更新：UPSERT

INSERT INTO user_terms (user_id, term, count, first_seen, last_seen) VALUES (?,?,1,?,?)
ON CONFLICT(user_id, term) DO UPDATE SET count = count + 1, last_seen = excluded.last_seen

「なければ作り、あれば足す」を1文で。先に SELECT して分岐すると、2つの同時リクエストでどちらも“無い”と見て重複や失敗が起きる。excluded.列 は「挿入しようとした値」。

3. このプロジェクトでは：失敗したら何が戻るか

失敗の場所 戻すもの 該当コード
検索（⑥）で例外 予約した 4,000 を全額払い戻し query.ts の catch → reconcileBudget(…, 0)
生成で例外 同上 同
Claude API のエラー 見積もり全額を払い戻し claude.ts の catch
成功 実測との差分 reconcileBudget(…, tokensUsed)
監査ログ 失敗したときは finalizeAuditLog を呼ばないので、仮の行が初期値のまま残る（tokens_used = 0） 失敗した試行も、回数としては“数える”

設計の確認: 「失敗しても、回数としては数える」「失敗したら、お金は払い戻す」。この非対称は意図したもの。

5. つまずきやすい点

  • 「確認 → 書き込み」を2回の往復にする。 同時に来ると破れる。条件を SQL に入れて1文にする。
  • 見積もりを“最後に”引く。 実行中に上限を超える。先に予約。
  • Promise.race だけでタイムアウトした気になる。 裏の処理は止まらない。abort() も。
  • ストリームを“1回の受信 = 1イベント”と決めつける。 切れ目をバッファで吸収する。
  • 失敗時の払い戻しを忘れる。 失敗するたびに予算が減り、使えなくなる。

  3. reserveBudget が false を返すのは、どんな SQL の結果のときか。
  4. Promise.race と AbortController の役割の違いは？
  5. ストリームで、受信を \n\n で区切って処理する理由は？

解答の方針

  • 演習 13.1: 上限 10,000 のとき → 予約 6,000+3,000=9,000 ≤ 10,000 成功（9,000）→ 清算 1,200-3,000=-1,800 → 7,200 → 次の予約 7,200+3,000=10,200 > 10,000 → 拒否（7,200 のまま）。上限 8,000 のときは、最初の予約 9,000 > 8,000 から拒否される。見積もりが実測より大きいと、予算が残っていても拒否される（画像つきの質問で、見積もりが過大にならないよう固定値にしている理由。claude.ts のコメント）。
  • 演習 13.4: INSERT INTO audit_log (…) SELECT … WHERE (SELECT COUNT(*) FROM audit_log WHERE user_id = ? AND created_at >= ?) < 30 のように、確認と書き込みを1文にして、挿入された行数（meta.changes）が 0 なら拒否する（2.4 と同じ考え方）。ただし、仮の行を先に書く今の方式でも、目安としては十分。
  • 確認問題 3: UPDATE … WHERE used_tokens + ? <= limit_tokens が 0 行だったとき（meta.changes = 0）。

# チュートリアル生成の質を上げるための分析と改善（2026-10-31）

**目的:** 「チュートリアルとしての質」を上げるために、(1) 参照している資料（出典）が使われているか、(2) 比較対象の道具との違い、(3) 習熟の過程で何が問題か、を調べ、生成エージェントを直す。
**読む前に:** 数字は、手元の生成ログ（`localRAG/tutorials/*_metrics.json` の 12 件）と、公開された説明からのもの。**件数が少ない**ので、傾向として読む。比較対象の道具は、実際に動かしていない（[比較資料](comparison-houdini-mcp.md)と同じ）。

## 1. 出典（source）の上限は、上げても効果が薄い

| 見たこと | 結果 |
|---|---|
| 現在の上限 | チュートリアル生成は **6 件**（`RAG_LIMIT`）。5 件はチャットの既定値 |
| 引用率 | 10 件の平均が **15%**。6 件中 0 件引用が **6 回**。最大でも 50% |
| 取れていた資料 | 「H22 VFX \| 破壊 FX & Pyro FX \| SideFX」のような**紹介・概要のページ**と、「Dynamics examples」など。ノードごとのパラメータ解説ではない |
| 検索の回数 | **生成の最初に 1 回だけ**。クエリは、トピックの文そのまま。結果はシステムプロンプトに固定され、**組み立ての途中では引き直せなかった** |

**判断:** 問題は件数ではなく、**「いつ・何で引くか」**。上限を増やすと、概要ページが増えるだけになりやすい。→ 生成の途中で引けるツールを足した（§4）。上限（6）は、効果を測ってから決める。

注意: 引用率は、モデルの自己申告（`finish_tutorial` の `sources_used`）。0% は「使われていない」とは限らない。

## 2. 比較対象との違いは、ツール数よりも「資料を引ける時機」

| | 資料の引き方 |
|---|---|
| fxhoudinimcp | 同梱マニュアルの全文検索（3 ツール）。AI が必要なときに呼ぶ |
| Houdini21MCP | `search_docs`（BM25）と `get_doc`（1 ページ全文）。AI が必要なときに呼ぶ |
| 本システム（以前） | 最初に 1 回の検索だけ。途中で引く手段なし |

比較した道具は、チュートリアルを作らないため、**生成物の質を直接は比べられない**。「ツール数の差が、質の差になる」は仮説で、§5 の方法で測る。

## 3. 習熟の過程の問題（HLS の資料との対応）

Inside The Mind の解説（Houdini Learning System、HLS）が挙げる 5 つの問題に、現状を当てはめた。

| HLS が挙げる問題 | 現状 | 対応 |
|---|---|---|
| ① 受け身で真似するだけ | 手順書・動画を「読む」形 | 次の段階で、パネルで要件を判定（未実装） |
| ② 試行錯誤の欠如 | `experiments` は AI が試した結果を書くだけ | `try_parameter` で、**数値つきの実験**を書かせる。学習者が試す流れは未実装 |
| ③ パラメータの場所探し | パラメータ画面の撮影はある | `get_parm_schema` で、**Parm パネルのタブと表示名**を手順書に書かせる |
| ④ 理解の自己検証がない | 各章の確認ポイント（数値・見た目） | **クイズは採用しない**（下記） |
| ⑤ 自力で作り直す練習がない | `next_steps` の文章だけ | 結果の条件だけを書く作り直し課題（未実装） |

**クイズを採用しない理由:** AI が作る問題は、答えの正しさを保証しにくい。読み物の形では、答え合わせにも意味がない。HLS のクイズは、Houdini の中で判定できるから成り立っている。代わりに、**実際のグラフから機械的に作れる確認**（数値の確認ポイント、結果の条件）を使う。

## 4. 実装したこと

| 内容 | 場所 |

| 生成の途中でドキュメントを引くツール `search_docs`・`get_doc`。引いたページは出典に続き番号で登録 | `houdini/python_panels/doc_tools.py` |

| 値を並べて試して元に戻す `try_parameter`（点数・サイズなどの表） | `houdini_tools.py` |
| 全体点検 `validate_network`（エラー・警告・末端が複数） | `houdini_tools.py` |
| 途中でビューポートを撮影して見る `view_viewport`（960x540・8回まで・`frame` 指定可）、`inspect_geometry` の `frame`（N フレーム目の数値） | `houdini_tools.py`、`tutorial_agent.py`（画像を tool_result に添える） |
| `promote_parameter`（子→親の Parm パネルへ昇格。現在の値を引き継ぎ、元は参照式）、`layout_network`（整列） | `houdini_tools.py` |
| `press_button`（キャッシュ書き出し）。押せるボタンは 4 種、ファイル指定が保存先フォルダの下のときだけ、10 回まで | `houdini_tools.py`、保存先は `tutorial_agent.py` がプロンプトで伝える |
| Graph タブを **Docs タブ**（ドキュメントを探して読む）に置き換え。`graph_view.py` は削除 | `docs_view.py`、`rag_chatbot.py` |
| 効果を測る指標（`doc_tools`・`doc_searches`・`doc_reads`・`rag_initial_extraction_rate` など）と、集計スクリプト | `tutorial_agent.py`、`scripts/compare_tutorial_metrics.py` |

安全の面: 検索先は、最初の検索と同じナレッジに固定（モデルは選べない）。ネットワーク呼び出しは Houdini のメインスレッドで実行しない。1 回の生成で 30 回まで。`try_parameter` は、どの途中の失敗でも元の値に戻す。式・キーフレーム・ランプ・シミュレーション系は拒否する。

## 5. 効果の測り方（これから）

出発点（実装前、12 件）: 完了率 0.83／反復 52.6／cook の失敗 0.42／差し戻し 0.33／費用 $0.289／引用率 0.15。

```bash
# 「ツールなし」で生成するとき（環境変数で外す。指標の doc_tools=false に記録される）
$env:RAG_TUTORIAL_DOC_TOOLS = "0"
# 「ツールあり」は、環境変数を消して（既定）生成する
uv run python scripts/compare_tutorial_metrics.py          # doc_tools の有無で比べる
uv run python scripts/compare_tutorial_metrics.py --by domain
```

同じ題材を、**ありとなしで、それぞれ 3 回以上**生成して比べる。見る指標: 完了率・cook の失敗・差し戻し・設計点（`lesson_score`）・引用率（`rag_initial_extraction_rate` は従来と同じ土俵）・費用。**費用は増える可能性が高い**（検索の往復と、ページ全文が会話に残るため）。質の向上と費用の増加を並べて判断する。

- 本番の Worker への反映（`/docs/list`・`/docs/get` は、デプロイするまで使えない。デプロイは別途の許可が要る）。デプロイ前は、Docs タブとドキュメント検索ツールは「404」のエラー文を返し、生成は止まらない。
- `fts_rowid` 順でチャンクを並べ直す前提（登録は先頭から順に挿入する）。本番のドキュメントで、先頭から末尾の順に読めるかは、デプロイ後に確かめる。
- 質の向上そのもの（§5 の比較はこれから）。

## 7. 実装後のレビューで直した点（2026-10-31）
| 見つけたこと | 直したこと |
|---|---|
| Docs タブを閉じたときに、通信中のスレッドが先に壊れて Houdini が落ちる恐れ | 実行中の仕事をモジュールで持ち、閉じたあとに届いた結果は無視する |
| `doc_tools` と `rag_client` に、同じ通信処理が2つあった | `rag_client.post_json` / `error_message` に一本化 |
| ナレッジの選び方などの純粋関数が、Qt を要する `docs_view.py` にあり、通常のテストでは飛ばされていた | `doc_tools.py` に移し、Qt なしで毎回テストする |
| `get_parm_schema` の既定値が「(1000)」と出る（実物の `defaultValue()` は1成分でもタプル） | 1成分は値だけを出す。テストの偽物も実物と同じ形にした |
| `try_parameter` が文字列パラメータを、展開後の値で戻す（`$HIP/…` がパスに変わる） | 展開前の値（`unexpandedString`）を覚えて戻す |
| `validate_network` が、SOP ソルバーの中（DOP の中の SOP）を「末端が複数」と誤検出し得る | 対象を、ふつうの SOP ネットワーク（geo・sopnet・SOP の subnet）に限る |
| `get_parm_schema` の連打が、「調べてばかり」の催促の対象外 | 対象に追加 |
| 教え方のルール（`lesson_design`）が、実験は `set_parameter` + `cook_node` と書いたままで、システムプロンプトと食い違う | `try_parameter` 優先に統一 |
| `/docs/list` の絞り込み語に長さの上限がない | 200 文字で切る |

残っている懸念: `/docs/list`・`/docs/get` には、回数の制限がない（`/search` の制限は、監査ログの件数で数えており、この2つは記録しないため）。キーを持つ人だけが呼べ、1回の読み取りは小さいが、D1 の読み取り量の上限を意識する場合は、制限の追加を検討する。

## 8. 追加した操作の安全面（`press_button` を中心に）
ディスクに書く `press_button` は、次の制限をすべて満たすときだけ動く。
- ノードがサンドボックスの中にある。
- ボタンが `execute`・`generate`・`bake`・`build` のどれか（それ以外は押せない。ボタンの一覧を返す）。
- ノードの**ファイル指定のパラメータ**（`FileReference` 型）が、すべて保存先フォルダ（`logs/tutorial_agent/cache/<サンドボックス名>/`）の下にある。`..` や、似た名前のフォルダ（`…_evil`）は外と判定する。空のものは未設定として扱う。
- 1 回の生成で 10 回まで。押す前に監査ログへ記録する。書き出しの合計が 500 MB を超えたら警告する。

限界: ファイル指定が `FileReference` 型でない独自のパラメータ（スクリプトで書き出すノードなど）は検査できない。押せるボタンが 4 種に限られること、保存先が既定でサンドボックス専用であることで抑えている。実機での挙動（`filecache` のボタン名、書き出しの所要時間）は未確認。

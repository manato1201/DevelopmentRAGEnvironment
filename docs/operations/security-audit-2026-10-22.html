2. 確定した問題

F1. Backlog の OAuth が、任意のホストへ Client Secret を送る（高）

  • 経路: GET /admin/oauth/backlog/start?owner=me&space=<任意のホスト>。owner=me（自分専用の接続）は、ゲスト以外の誰でも使える。以前の normalizeSpaceUrl は、https://<入力されたホスト> を、そのまま通していた。
  • 悪用: 開始 → Worker が <ホスト>/OAuth2AccessRequest.action へリダイレクト → そのホスト（攻撃者のサーバー）が、code と state をつけてコールバックへ戻す → Worker が、<ホスト>/api/v2/oauth2/token へ client_id と client_secret を POST。攻撃者が、Backlog アプリの Client Secret を受け取れる。 保存済みの接続のトークン更新にも、同じ経路があった。
  • 前提: BACKLOG_OAUTH_CLIENT_SECRET が設定されていること（この環境で設定済みかは、未確認）。
  • 修正: スペースのホストを、*.backlog.com / *.backlog.jp / *.backlogtool.com に限った（ポート・ユーザー情報つきも拒否）。開始・コールバック・トークン更新の3か所で検査する。
  • 確認: 13種類の細工したホスト（backlog.com.evil.com・ポート付き・@ 付きなど）を拒否するテスト。細工した state と、保存済みの悪いホストでも、何も送られないことを確認。
  • 推奨（あなたの作業）: すでに Backlog の OAuth アプリを登録していたなら、念のため Client Secret を作り直すことを検討してください（漏れた形跡は、私には確認できません）。

F2. OAuth の開始URLに、APIキーを載せている（中）

  • 開始は、ブラウザの直接の移動なので、Authorization ヘッダーを付けられず、?key=<APIキー> を使っていた。URL は、ブラウザの履歴・アクセスログ・Referer に残る。
  • 修正: POST /me/oauth-start-token で、60秒・1回だけ使えるトークンを発行し、開始URLには ?t=<トークン> を付ける。画面は、これを使うように変えた。トークンは、別のサービス用の state では使えない。
  • 残り: F8。

F3. エラー文を、エスケープせずに innerHTML へ（低）

  • innerHTML = '…' + e.message + '…' が13か所。サーバーのエラー文には、入力の一部（例: ツール名）が入ることがある。悪用には、被害者の画面で、攻撃者の文字列が入るエラーを起こす必要があり、筋は狭い。ただし、画面は localStorage の APIキーで動くため、成立すると影響は大きい。
  • 修正: esc() を通す。

F4. state の消費が、2回の操作（低）

  • SELECT のあと DELETE。同じ state のコールバックが同時に2回届くと、両方が通る余地。state を知るのは、本人のブラウザだけなので、悪用は難しい。
  • 修正: DELETE ... RETURNING の1回の操作に。

F5. クリックジャッキング（中）

  • 画面に X-Frame-Options も frame-ancestors も無かった。他のサイトが、この画面を枠に入れ、見えない状態で重ねてボタン（管理の削除・書き込みの「実行」など）を押させられる。画面は、ブラウザに保存したキーで動くため、枠の中でも、持ち主の権限で動く。
  • 修正: 画面と OAuth の結果ページに、X-Frame-Options: DENY・Content-Security-Policy: frame-ancestors 'none'・X-Content-Type-Options: nosniff・Referrer-Policy: no-referrer。

3. 却下・要確認

  • F6（却下）: urlImport は、ナレッジ登録権限者が、任意の公開URLを取り込む機能。Workers は、内部のネットワーク（メタデータの宛先など）へ届かない。取り込んだ内容は、ナレッジとして保存される（仕様どおり）。
  • F7（却下）: APIキーは、crypto.getRandomValues の32バイト（256ビット）。総当たりが成り立たないので、ソルトは要らない。
  • F8（要確認）: ?key= を残してあるのは、古い画面・手作りのURLのため。使われていないと確認できたら、削除してください（削除すると、キーが URL に載る経路が、完全になくなります）。

4. 点検した範囲（問題が見つからなかったもの）

  • 認証（auth.ts）: キーの照合は、ハッシュの完全一致。期限切れは、「存在しない」と同じ応答（キーの存在を教えない）。個人用 namespace は、本人だけ。
  • OAuth の state（oauthConnections.ts）: ランダムな UUID・10分で失効・1回だけ・サービスごと。接続の持ち主（owner_id）は、開始時に決めて state に入れる。
  • MCP（src/mcp/）: 接続先は、登録簿の URL だけ（任意の URL は受け付けない）。書き込みは、本人専用・明示的な許可・確認（1回だけ・5分・本人のみ・保存した引数だけを実行）。監査ログに引数を残さない。
  • 秘密の扱い: コードに、秘密の値は入っていない（wrangler secret で保存）。

5. 見ていないもの（次の点検の対象）

  • Google 系 OAuth（calendarOAuth.ts・Drive・Gmail）と Jira・Slack のコールバックの細部（共通の state の部分は確認したが、各サービス固有の処理は、深くは見ていない）。
  • kbAdmin.ts・keyAdmin.ts の権限（requireAdmin の付け忘れ）の網羅的な確認。
  • Cloudflare 側の設定（WAF・レート制限・Bot Fight Mode）。

# ライセンスと権利の点検（2026-11-21）

法的な助言ではなく、リポジトリと配布物を実際に調べた結果と、決めるべきことの整理です。法的な判断が要るもの（★）は、大学の知財窓口・SideFX・専門家に確かめてください。

## 1. いまの状態

| 項目 | 状態 |
|---|---|
| `DevelopmentRAGEnvironment` / `RAGReel` | どちらも **Public**。`LICENSE` が **無い**（GitHub の licenseInfo も null） |
| 無いとどうなるか | 既定は「全権利留保」。他人は読む・GitHub 内でフォークするのはできるが、**使う・改変する・再配布する権利は与えていない**。守りとしては、いまは強い側 |
| 弱い点 | 「誰に何を許すか」が書かれていない。実証実験の参加者・指導教員・企業にも、使ってよい範囲を示せない。取りっぱぐれ（クレジット・収益）を防ぐ根拠も、文書としては残っていない |

## 3. 権利まわりの、見つけた論点（★は要確認）

1. ★ **Houdini は Education Edition（画面のタイトルバーに出ている）で開発・撮影している。** Education 版の利用条件は、教育目的に限られ、商用の成果物に使えないのが一般的です。**収益化する場合は、開発・撮影に使うライセンスの種類（Indie / FX など）を、SideFX に確認する**必要があります（Reference の撮影画像・動画の素材も、同じ扱いになりえます）。
2. ★ **SideFX の公式ドキュメントの扱い。** RAG（Worker の知識）に取り込み、Reference の説明の材料にしています。Reference の説明は AI が日本語で書き直したものですが、元は SideFX の著作物です。**収益化・再配布の前に、SideFX の利用条件を確認する**。
3. ★ **HoudiniReference・YouTube などの抜粋。** 題名・出典・URL・短い抜粋だけを使い、出典のページへのリンクを出しています（リンクと短い引用の範囲）。`yt-dlp` で取った動画の字幕・音声を、RAG に入れて配る場合は、各サービスの規約に触れうるので、**配る範囲に入れない**のが安全です。
4. **RAGReel の配布物（インストーラ）に、第三者のライブラリが入っている。** `vcpkg.json` に Qt（LGPL）と FFmpeg（既定は LGPL）があり、インストーラは DLL を同梱しています。LGPL は、**ライセンス文・著作権表示を同梱し、DLL を差し替えられること**を求めます。いまのインストーラ（`ragreel.iss`）には、ライセンス文の同梱がありません。→ 配布する前に、`THIRD_PARTY_NOTICES` を同梱する（下の §5）。FFmpeg が GPL の部品を含むビルドでないことも確認する。
5. ★ **大学の知財規程。** 卒業研究の成果物（コード・データ・論文）の権利が、大学・指導教員と、どう分かれるか。公開・ライセンス・収益化の前に、確認する。
6. ★ **参加者のデータ。** 事前アンケート（経験・学習背景・実務経験・ツール歴。自由記述あり）・課題の記録・チャットの質問を、サーバーに保存している。**同意を取る文面と、削除の窓口**が、画面の中には無い（運営の説明の側にあるはず。`docs/pilot/houdini21-learning-effect-study.md` の §9）。論文に出す・配る前に、同意の範囲を確かめる。
7. **GitHub の Contributors に `claude` が出ている。** いまの履歴には Co-Authored-By が 0 件なので、GitHub の集計に、以前の分が残っているだけの可能性が高い。気になるなら、GitHub のサポートに問い合わせる（履歴の書き換えは、しない）。

## 4. 取りっぱぐれを避けるための、選択肢

目的が「実証実験と論文には、自由に使ってもらう。収益化・商用利用の道は、自分で持っておく」なら、次の順で合います。

| 案 | 中身 | 向き・不向き |
|---|---|---|
| **A. 全権利留保を、明文にする**（独自の `LICENSE` / `EULA`） | 閲覧のみ可、使用・改変・再配布は許可制と、書く | 最も守れるが、学生・研究者が使ってよいかが、毎回、問い合わせになる |
| **B. ソース公開で、非商用だけ許す**（PolyForm Noncommercial 1.0.0 など） | 学習・研究・個人の使用は、誰でも自由。**商用は、別契約** | 実証実験・論文・学生配布と、収益化の両立。**おすすめ**。ただし「OSS」とは呼べない（OSI の定義外） |
| **C. 一定期間後に OSS 化**（Business Source License 1.1 など） | 当面は商用を制限し、決めた日に MIT 等へ移る | 将来の公開を約束したいとき。条件の設計が少し重い |
| **D. MIT / Apache-2.0** | 誰でも、商用を含めて自由 | 取りっぱぐれは防げない（利用者への請求の根拠が無くなる）。実績づくり・採用目的なら |

どの案でも、次を決めます: 権利者の表記（個人名か、所属か。§3-5 の確認が先）、`RAGReel`（別リポジトリ）にも同じ文面を置くか、Houdini の SideFX の資料・商標の扱い（SideFX の製品名は、商標）。

## 5. GitHub の Release にインストーラを置けるか

**できます。** 1 ファイル 2 GiB まで（`RAGReel-Setup-1.1.0.exe` は 約 47 MB、パネルの zip は 約 0.4 MB）。`gh release create` で、タグ・説明・ファイルをまとめて作れます。`gh` は、このPCで、`manato1201` としてログイン済み。

置く前に、次を済ませると安全です。

1. §4 で、ライセンスを決めて、`LICENSE` を入れる（公開されるファイルに、使ってよい範囲が書かれている状態にする）。
2. `THIRD_PARTY_NOTICES`（Qt・FFmpeg・MSVC ランタイムなどの表記と、ライセンス文）を、インストーラと、リポジトリに入れる（§3-4）。
3. インストーラに、鍵・URL が入っていないことを確認する（パネルの zip は、`install.ps1` が、URL とキーを、インストール時に聞く作りなので、入っていない。**`RAGReel-Setup` は、まだ中身を開けて確かめていない**）。
4. 置く場所: パネルの zip は `DevelopmentRAGEnvironment`、動画エンジンのインストーラは `RAGReel` の Releases が、持ち主に合う。ただし、利用者が 1 か所で全部取れるよう、片方にまとめて、もう片方から案内する形でもよい。
5. Release は、**公開した瞬間から、誰でも取れる**（あとで消しても、すでに取られたものは戻らない）。1〜3 が終わってから。

Release に置くと、`install.cmd` の配布（いまは、人に直接渡している）を、URL 1 つで案内できます。バージョン（`1.1.0`）と、zip の名前（日付とコミット）の付け方も、そろえておくと、更新の案内が楽です。
